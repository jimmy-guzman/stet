# Agent instructions

`stet` is a read-only companion TUI for CLI coding agents (claude code, opencode, codex). You run an agent in one terminal pane and `stet` in another to inspect what changed: everything an IDE shows you, nothing it does for you. **It only inspects. It never reviews, explains, approves, rejects, gates, talks to an agent, or writes to the repo.** That constraint shapes every change here.

See the repo-root `README.md` for what stet does, its keys, and its non-goals; see `SPEC.md` for the implementation invariants behind those features; see `TASTE.md` for the craft bar every interface surface clears. Read SPEC before changing tree construction, the viewer, recency, scopes, or worktrees, and TASTE before adding or reworking any UI surface.

## Stack

- Bun for runtime, scripts, dependencies, tests, and build.
- TypeScript with `strict` enabled.
- `@opentui/core` and `@opentui/solid` (SolidJS fine-grained reactivity); JSX configured with `jsxImportSource: "@opentui/solid"`, and `@opentui/solid/preload` in `bunfig.toml`. Solid is the rendering layer OpenTUI's own authors use; its surgical updates avoid the whole-tree re-render churn that a React reconciler submits to the native renderer.
- **Whether stet can run at all is settled before the renderer, and every git refusal is one actionable line.** `main.tsx` resolves the repository through `Git.repoContext` on a **second short-lived `ManagedRuntime`**, exactly the precedent the config load sets and for the same reason: the app runtime's first use builds `DiffEngineLive`, whose highlighter warm-up (attaching the active syntax theme, ~2ms) must stay behind the first paint. The `highlights` WebAssembly module itself compiles at import (~10ms), before the paint, because `file-support/config.ts` validates `files` syntax names with its `isSupportedLanguage` while the config loads. It is one O(1) read, so a launch outside a repository prints on the normal terminal instead of flashing an empty shell. The classification is pure in `src/git/repo.ts` (`repoContextArgs`/`parseRepoContext`, `classifyRepoOutput`/`isMissingGit`/`classifyRepoFailure`, `bareCheckArgs`, `repoFailureMessage`/`unknownRefMessage`, `refTreeArgs`/`isRevisionRange`, `emptyTreeForFormat`), the git-domain template pattern, and the service wraps it so `GitError.message` **is** the line to print. Never widen a message to quote the invocation or git's full stderr: `git rev-parse --path-format=absolute --show-toplevel --git-common-dir failed with exit 128` plus three lines of `use '--' to separate paths` is what #345 reported, and `error.stderr || error.message` is how that string sneaks back in (`CommandError.message` embeds the invocation). **Classify on a signal git does not translate.** Its stderr is localized, so matching `not a git repository` classifies an English user and drops every other one: the too-old-git case is read off **stdout** (`rev-parse` echoes an option it does not recognize and exits 0, so the parse requires two absolute paths and a format token that is not an option), and bare-versus-absent off a second command's exit code (`git rev-parse --is-bare-repository`, asked only after the context read fails). **A ref is explained, never gated.** `rev-parse --verify` accepts objects `git diff` rejects (a blob) and rejects arguments it takes (a revision range, an unborn `HEAD`), so gating a launch on it both blocked working invocations and let broken ones through; `Git.refIsDiffable` runs only when the startup load has already failed, exempts ranges, and answers `true` whenever it cannot tell. **An unborn `HEAD` is not one of these failures.** Every other `HEAD`-touching read degrades on exit 128, but a diff has no degraded answer, so the base is resolved rather than tolerated: startup calls `git.headRef` **before** `changedFiles`, and an unborn `HEAD` (which `headRef` reports as `undefined`, never as a substituted sha) makes the base the repository's empty tree (`state.headUnborn` -> the `baseRef` memo that `all`/`staged` read). `headUnborn` means "the base is the literal `HEAD` **and** `HEAD` is unborn": an orphan branch leaves every other ref resolvable, so substituting a ref the user named would silently diff against nothing. The drain's `repairBase` repairs it in both directions (born on success while substituted, unborn on a failed read), since neither is observable from the other side. `scopeLabel` takes the repository's empty tree and renders a ref equal to it as `no commits yet`, never its sha, which also keeps it from crowding the branch off the header; it compares the scope's own ref rather than `headUnborn`, since a scope picked during the startup load keeps the ref it was given while the signal moves on without it. **That empty tree is the repository's, read once and never named as a constant.** Its sha follows the repository's hash algorithm, so a `git init --object-format=sha256` repository has a different one and the SHA-1 literal names an object its database does not contain, which git rejects outright. The preflight `rev-parse` therefore carries `--show-object-format` as a fourth option (free: it landed in git 2.29 and `--path-format` in 2.31, so any git that accepts the latter understands it) and `RepoContext.emptyTree` carries the answer to `state.emptyTree`, resolved once for the session since linked worktrees share one object database. So the git service names no empty tree at all: `headRef`/`parentRef` answer `undefined` and `Commit.parent` is optional, and the substitution lives only where a diff endpoint is built. The drain's `last-commit` re-resolve must compare against the **substituted** ref, never the raw parent, or a root commit re-sets the scope on every tick and resets the viewer's cursor and scroll. See SPEC's Startup and Scopes sections.
- Git output is the source of truth for the file map: the app shell paints immediately from the empty model and the initial git load seeds it in the background (so a large repo shows the UI at once instead of a blank screen during the load), and a filesystem watcher (debounced, over the worktree tree plus the resolved git dir) keeps it current, with an adaptive safety poll as the floor that covers anything the watcher misses. Refresh triggers feed conflating sliding-1 queues, so a burst of changes collapses to one in-flight read plus one trailing run rather than a backlog; the changed set drains on every tick, while the full repo-file list re-lists only when the changed path-set shifts (plus a slow floor), not on a blind timer.
- The diff/file viewer is stet-owned (`src/diff/`, `src/components/diff/diff-view.tsx`): `@pierre/diffs` is the headless engine (patch parse + syntax highlight on its `highlights` backend, `@pierre/highlights`' bundled WebAssembly lexers, chosen over Shiki because it tokenizes a 4k-line file in ~35ms where `shiki-wasm` took ~500ms), and lays out the diff's row stream (`DiffHunksRenderer`, through stet's `WholeLineRenderer` subclass, which stops it cutting a line past the 5000-character highlight limit, read by `rowsFromHunks`), and stet hand-renders the windowed rows on OpenTUI primitives rather than using the built-in `<diff>`. Syntax colors come from the active theme itself, which is always a Zed-format theme (the only shape the `highlights` backend reads) registered with `registerCustomTheme(..., "zed")`; there is no tree-sitter path. Only one highlighter backend can be active per process, and `highlights` has lexers for ~150 languages (fewer than Shiki), so a language it lacks renders as plain text; `files` syntax names are validated with its `isSupportedLanguage`. File support resolves in exactly one place, `src/file-support/`: named associations select syntax and icon facets independently by exact filename, glob, extension, then dotfile specificity, with `@pierre/diffs` filename inference as the final syntax fallback. `languageForPath` in `src/diff/engine.ts` is only the syntax-facing adapter; the diff, fold model, search results, and icons all consume the same registry. Add a file type through `builtinFiles` or config (an icon for a type Trees lacks goes in `icon-resolver.ts`'s `fallbackExtensions`, per the icon bullet below), never a new resolver branch. A changed file is diffed in-process from the scope's two endpoints (`src/git/file-patch.ts` reads them, and the engine diffs them with `parseDiffFromFile` on `@pierre/patches`, a WebAssembly jsdiff drop-in that also computes the changed-word marks), not by `git diff <ref> -- <path>`: git's pathspec-limited diff-index costs seconds per open in very large repos (#188) while blob/worktree reads stay O(path depth). `@pierre/patches` has no deadline and runs synchronously, so `buildDiffInput` bounds the worst-case Myers cost `(N+M)·D` before handing the files over, with `D` bounded from the text itself (numstat can be stale by the time a side is read, and an index side can change under it): first by the lines between the common leading and trailing characters, then, for edits spread through the file, by `N + M - 2L` over patience diff's common subsequence (the order-kept lines unique to each side, plus the equal lines at either end of each gap between them, which catches repeated lines like `}`), and a one-sided add or delete is exempt since it is linear. The pathspec `git diff` survives only as the fallback in `Git.fileDiff` for sides an in-process diff can't reproduce or bound (missing/oversized, one-sided CRLF, identical text against non-zero numstat, cost over budget). See SPEC's Viewer section.
- The terminal tree model is `@pierre/trees`' public vanilla `FileTree`, owned by `state` through `src/tree/model.ts`. OpenTUI requests `treeSlice(start, height)` and `treeRowCount()`; never materialize the full visible-row list in state or components. The adapter appends NUL to file model paths so a deleted file and a same-named directory can coexist across Git endpoints. Directory model paths end in `/`. Only the adapter sees these identities: rows, navigation, clipboard, and Git/filesystem calls use original paths. Git metadata remains in path-keyed records, including directory counts, stage states, and warnings. Use Trees' default natural ordering and match its folder controls through public item handles: Right expands or advances, Left collapses or focuses the parent, and Enter toggles. Home and End focus the visible endpoints. File activation makes one viewer navigation. Content refreshes update decorations without rebuilding topology; path changes use batched additions/removals, update file counts from path differences, and prune orphaned directories. Trees owns live focus and expansion; state actions call the adapter directly, and rows carry Trees' expanded flag. The adapter remembers focus and expansion intent across filtering and deferred loading, replaying expansion only for new or restored directories. Model subscriptions invalidate Solid readers only; they never open files or write navigation history. The owning memo unsubscribes and calls `cleanUp()` when the worktree changes, on state disposal, and on test reset. Keep model-only compatibility tests when upgrading Trees because its root export also includes a browser renderer.
- Clipboard copy goes through OpenTUI's clipboard (`createClipboard`: the system clipboard, then OSC 52), with no external tool. The terminal half needs the renderer, so `main.tsx` composes it and registers it through `src/clipboard/registry.ts`, which keeps the renderer out of `state`; the `Clipboard` service is the only reader. A test sees no clipboard unless it registers one (`recordClipboard` in `test/helpers.ts`), so no test can reach the real one, and the preload clears it.

## Conventions

- Read `.agents/skills/opentui/SKILL.md` before any OpenTUI code. For Bun, read the Bun API docs in `node_modules/bun-types/docs/**/*.mdx` before any dependency/script/build change; they ship with the installed `bun-types`, so they match the pinned version.
- Prefer `bun run`, `bun test`, `bun install`, `bun add`, `bun add -d`, `bun remove`, `bun build`. No Node/npm/Jest/esbuild wrappers unless explicitly requested. Runtime flags go before `run` (e.g. `bun --watch run <script>`).
- Keep `bun.lock` changes paired with dependency changes. Declare direct dependencies in `package.json`; don't rely on transitive ones.
- Pin every `dependencies` and `devDependencies` entry to an exact version (no `^`/`~`). stet ships as a compiled binary (`private: true`, `bun build --compile`), so the manifest mirrors the lock and every bump is an explicit, reviewable edit; caret ranges only help library consumers dedupe, which never applies here.
- Lint and format are oxlint and oxfmt, run from the repo root (`bun run lint`, `bun run fmt`), not from within `packages/tui`: oxlint resolves this package's `oxlint.config.ts` (the root config plus `ultracite/oxlint/solid`) on its own when invoked from the root, and oxfmt uses the root `oxfmt.config.ts`, so a single root-level command already covers the whole repo. The rules are Ultracite's defaults (see the root `AGENTS.md`); fix a finding in code rather than overriding the rule. Do not add ESLint or Prettier.
- Dead exports are caught by knip (`bun run knip`, also part of `bun run check`). Remove the `export` keyword rather than suppressing.
- Git hooks run through lefthook (`lefthook.yml`, wired up automatically by its own postinstall on every `bun install`, no extra step). `pre-commit` runs on staged files only: one `bun --bun x ultracite fix` job formats, applies safe lint fixes, and re-stages, and anything it cannot safely fix still blocks the commit. `pre-push` runs only `typecheck` (root `bun run typecheck`, fanning out to both `packages/tui` and `docs` via `bun run --filter '*' typecheck`) and `knip` (tui only, per `knip.json`'s `ignoreWorkspaces`), in parallel: those are the two checks that need the whole project graph and can't be scoped to staged files. `bun test` and full-project lint/format are deliberately left off pre-push (pre-commit already covers staged-file lint/format, and CI runs the full `bun run check` on every push/PR), since re-running the whole suite on every push was slow enough to be worth trading for CI as the actual safety net. Agents run the same hooks as humans; no skip/bypass config is layered on top of git's own `--no-verify` or lefthook's `LEFTHOOK=0`.
- Use `===` and `!==`; never `== null` or `!= null`.
- No explicit return type annotations unless needed for exported API clarity, recursion, overloads, or inference limits.
- Rely on type inference; avoid explicit annotations or interfaces unless needed for exports or clarity, and inline single-use values rather than naming them.
- Prefer `const`; use a (non-nested) ternary or early returns instead of reassignment, and early returns instead of `else`. Don't introduce a `let` just to hold a value for a later statement (e.g. across a `try`/`catch`); lift it into a helper or expression (wrap a throwing call in a `Result` rather than a mutable placeholder).
- Prefer functional array methods (`map`/`filter`/`flatMap`) over loops; use type guards on `filter` to keep inference downstream. A `filter` followed by a `map` runs as one pass through iterator helpers (`xs.values().filter(f).map(g).toArray()`), which anti-slop's `no-array-filter-map` requires. A fold is the exception: `no-array-reduce` rules out `reduce`, so an accumulation is a `for...of` over a `let` accumulator.
- For generic data utilities, prefer native ES2024 over a third-party util library: `Map.groupBy`/`Object.groupBy` for grouping, in preference to a hand-rolled get-or-create-push loop (`Map.groupBy` returns a `Map`, which a `Record`-returning lib helper does not), `new Set`/`Set` methods (`union`/`difference`/`intersection`) for dedupe and set algebra, `toSorted` with an explicit comparator (use `localeCompare` for locale-aware order), and `structuredClone` for deep copies. Project-specific pure helpers (no Effect/Solid/OpenTUI imports) live under `src/utils/`; domain helpers stay in their domain module.
- Use Bun APIs where they exist (`Bun.file`, and so on).
- Never alias imports (no `import { x as y }`).
- Use the `@/` path alias (mapped to `src/` in `tsconfig.json`) for cross-directory imports (`@/state`, `@/diff/follow`), not upward-relative chains (`../../diff/follow`). Keep same-directory `./sibling` imports relative, since they signal colocation. Tests import source through the alias too (`@/git/activity`), not `../src/...`.
- Prefer dynamic imports for heavy modules on startup-sensitive paths; bind them at the top of the narrowest scope that needs them, and keep branch-specific imports inside their branch so the git tree renders before anything heavy loads.
- Do not reach for `as`, `!`, or `any` without first exhausting proper solutions.
- Parse untrusted input with Effect `Schema` at the boundary, never with `typeof` checks over `unknown` (anti-slop rejects both `unknown` parameters and runtime `typeof`). User config is JSON, so its registries are `Schema.JsonObject` and each resolver decodes an entry's fields with small schemas, keeping its own issue text. Discriminate an already-typed union with the `Predicate` module (`Predicate.isString`), not `typeof` or a hand-rolled `isRecord`. A function that receives an arbitrary thrown value names the parameter `cause: unknown`, the rule's one exemption; where a promise rejection needs handling, use `try`/`catch` rather than a `.catch` callback, since core requires `error: unknown` on that callback and anti-slop rejects it.
- Do not silence lint or type errors with rule overrides or casts. Fix the root cause.
- **A comment carries a why, never a what.** JSDoc carries a declaration's contract, and `TODO`/`FIXME` carry a known gap. A line comment earns its place when it holds reasoning the code cannot: a platform quirk, a race, a measured value, or the rejected alternative sitting one line away. Delete the ones that restate what the line below already says, since those are the ones that drift into lies. A JSDoc's description follows the same rule: prose that merely restates what the code plainly does is still noise. `@param`/`@returns` tags are welcome alongside that description (they surface on hover in editors, which the types alone do not), but tags never replace the why: when a docstring pass (a bot, a refactor) collides with an existing rationale block, merge the two, prose on top and tags below, never swap the prose out.
- Prefer small typed modules (git parsing, clipboard, CLI args, UI state), and structured parsing over ad hoc string manipulation when a command offers machine-readable output.
- Visual colors come from theme tokens in `src/theme` (`tokens.ts` shapes the `Theme`, `derive.ts` computes it from the active theme's palette, `resolve.ts` adds the RGBA variants, and `context.tsx` exposes them as the `theme` handle), never hardcoded hex at call sites. Each `<scrollbox>` must set `scrollbarOptions`: the thumb comes from the `scrollbar` token and the track stays `theme.rgba.transparent` so it inherits whatever surface it scrolls over (one track color can't match every surface). Without `scrollbarOptions` OpenTUI paints a loud default gray that ignores the palette. Do not pin `horizontalScrollbarOptions={{ visible: false }}` on a vertical-only scrollbox: since OpenTUI 0.8 a ScrollBox computes its range and shows or hides each bar natively from one layout, so a vertical-only box never shows the horizontal bar. The pin was the workaround for #363, when bar visibility came from the _previous_ layout pass and a stale horizontal bar ate the last row of an overlay sized exactly to its content (the help list's `q  quit` row, the worktree picker's current-worktree row); the guards in the help, worktree, and scope render tests still assert those rows.
- User-facing messages carry a severity through one taxonomy in `src/log/` (`levels.ts`: the `LogLevel` union plus `levelColor`, mapping to `severity.*`/`success`/`text.secondary` tokens, and `levelGlyph`, the bare text-presentation glyphs `✖ ⚠ ✓ ℹ`). Severity is always paired with its glyph, never signalled by color alone, so it reads under `NO_COLOR` and for colorblind users. Two renderers consume it: `status-bar.tsx` reads the level from the selected `StatusBarModel`'s message item and pairs `levelGlyph` with `levelColor`, and `log/terminal.ts` (`logError`/`logSuccess`/`logInfo`) prints pre/post-TUI lines, deriving ANSI from the active theme hex via `Bun.color(hex, "ansi")` gated on `Bun.enableANSIColors` (which honors TTY/`NO_COLOR`/`FORCE_COLOR`); `info` stays glyph-only there since the terminal background is uncontrolled. Glyphs must stay bare codepoints (no `U+FE0F`), or the variation-selector form renders two rows tall.
- **The header owns durable context; the status bar owns whatever is live right now.** The header carries repo/worktree identity, branch or commit subject, scope, and changed count, and does not change here. The status bar renders **one full-width item**, never a split, chosen by the pure `src/status/model.ts` (`buildStatusBarModel`) from a fixed ladder: foreground progress (a worktree switch), action notification, persistent alert, recent activity, then guidance. `state.statusBarModel` supplies the live inputs and `status-bar.tsx` only renders the selected item's `kind`. Guidance is the **lowest** tier and always has content, which is what makes the model total and every tier above it a pure displacement, so there is no fit negotiation between neighbours and no pair of items can disagree about who shrinks. Guidance is context-aware only for the temporary find modes (`enter find ─ esc cancel`, `n/N next/prev ─ esc clear`) and is otherwise `? help ─ q quit`; the panes get no standing tutorial hints, and overlay controls stay in their own overlay footers. **Routine successes are not status.** A completed worktree switch and the like say nothing: the durable UI they just updated is the completion signal, and a persisted success line outlives its usefulness. Only `warning`/`error` persist, as a `StatusAlert` **tagged by lifecycle** (`worktree-list`, `worktree-switch`, via `raiseAlert`/`clearAlertSource`/`latestAlert`): one untyped status channel was why two unrelated failures overwrote each other and either one's retry wiped the other, so a source clears only its own. A failed worktree list retries by reopening the picker and a failed switch by switching, so they are separate sources (browsing the picker must not retire an unretried switch error). The newest source owns the row. Each source retires its own alert when its next attempt starts. Fit is measured in terminal cells with `Bun.stringWidth`, including padding, marks, and gaps, never with JavaScript string length.
- Ambient activity is the recent changed file and nothing else (a message never rides beside it, since one tier owns the row): a `RecencyDot` leads its path, presented with the tree's changed-file cue rather than a neutral path or a number. The path is tinted by its git change kind (`gitModel().changedByPath.get(path)?.kind` -> `theme.colors.kind`), and both fade toward the background (path -> `text.faint`, dot `recency.fresh` -> `recency.aged`) across the 30s `RECENT_MS` window, so freshness reads as brightness and the row recedes silently as it ages (there is no "Ns ago" label). The dot is a shape, so "changed" survives `NO_COLOR` where the color-only kind tint would not; a leveled message still carries its glyph + `levelColor`. `RecencyDot` lives in its own `src/components/recency-dot.tsx` and renders only the mark (`●`); spacing is the caller's, passed as a `marginLeft`/`marginRight` so it stays gated to the dot's presence (the tree and file picker trail it with `marginLeft`, the status bar leads with `marginRight`). The path truncates from the left so the filename survives, and yields the row to guidance when it has room for nothing but the ellipsis. Adjacent same-color spans share one `<text>` because an empty `<text>` in a flex row paints a phantom cell.
- The two persistent panes (tree, viewer) have no box around them. The tree draws one `border.unfocused` line on the side that faces the viewer (`border={[side]}`), read from `layout().sidebar.divider`, and the viewer draws nothing, so both panes paint to the terminal edge. That frees the 3 columns the two `single` boxes used to cost. The header and status bars are the horizontal rules: each region in `app.tsx` paints a `border.unfocused` `─` backdrop across its one row (`ruleLine`, with a `┬`/`┴` tee at `layout().junction`, the column where a side-docked divider meets it), and the bar's text paints over it in `surface.base` islands padded by one space, leaving a rule cell at each edge. Fields inside a bar are separated by `BAR_SEP` (`─`, tinted as the rule), never a `·`, so the bar reads as one line broken by its fields; the header's budgets measure it like any other field. Both bars share one `Island` component (`src/components/island.tsx`) and the pure `src/components/bar.ts` (`BAR_EDGE`, `ISLAND_PAD`, `BAR_SEP`), which the header's `available()` and the status model's fit budget both read, so a bar's painted width and measured width move together. A rule in a row of its own was tried and rejected: a glyph fills its whole cell, so a centered `─` shows a blank strip on both sides and an edge block (`▔`/`▁`) on one, and either costs a row. Text wins over the tee where the two overlap. A zoomed tree faces nothing and draws no divider. Focus is the cursor highlight, and each pane paints its own only while it holds focus: the tree lights its cursor row only while `focusedPane` is `tree`, `DiffView`'s `isCursor` lifts the caret line only while it is `diff`, and the search view lights its selected result only while it is `search`. A viewer with no caret line (a binary preview, a placeholder) still has its title row: the path uses `text.primary` while the viewer is focused and `text.secondary` otherwise. When find replaces the title row, the find prompt's `/` carries the accent only while focused. A pane with nothing in it marks focus on its empty-state line (`nothing to inspect`, `no files`) through `emptyStateTone` (`src/components/focus-tone.ts`), `text.primary` while focused. A tree still in its deferred `repoFiles` load shows no text (that would flash before the rows arrive) but, while focused, paints an empty `surface.cursor` band on its first row as its focus mark until the rows load. Changes-only mode with nothing changed shows every file rather than an empty tree (the header's changed count says why), so it waits on the same load. So every pane always carries a mark. An open find bar owns the keyboard, so an effect in `state` closes it the moment `focusedPane` leaves the viewer (whichever path moved focus), the way `esc` would; a committed find (`n`/`N`) stays. Every one of these is a tone change, which survives `NO_COLOR` as brightness. The selection band stays visible while the viewer is unfocused, because it is content and not a focus mark. Separate the bars with the rules, never by banding them with a different surface: a terminal window is rarely a whole number of rows tall, so the emulator paints a few spare pixels below the last row in its own background, and a status row that differs from `surface.base` makes that strip read as a gap. Overlays (dialogs, comboboxes, menus) keep a full `border.focused` box, since a modal layer is always the active surface.
- Every focused `<input>` must set `focusedTextColor` (and `focusedBackgroundColor`) alongside `textColor`/`backgroundColor`. OpenTUI's input caches separate focused/unfocused colors at construction, and the OpenTUI/Solid reconciler builds the renderable with only `{ id }` then applies props through setters; the `textColor` setter updates only the _unfocused_ color, so a focused input that omits `focusedTextColor` renders its text in the default white regardless of `textColor`. Dark themes mask this (white-on-dark reads fine); light themes show white-on-light typed text. Same applies to any focused-only color: set the `focused*` variant explicitly, never assume it inherits from the base.
- User config lives in `src/config/` (a normal domain: pure `paths`/`schema`/`load` plus a `Config` service), read from `~/.config/stet/config.jsonc` (honoring `$XDG_CONFIG_HOME` when set, with `~/.config` as the fallback base; `config.json` is the second candidate, and `configPaths` lists the candidates in priority order, both parsed as JSONC) once at startup. The schema is shaped by feature: each section owns its settings including its off switch (`icons: { enabled, glyphs }`, `viewer.wrap`, `sidebar: { open, width, height, position, changesOnly }`, `update.check`, `search: { regex, caseSensitive, scope }`, plus the flat `editor`/`ide`/`theme`/`files`/`keybindings`). **What an omitted key means is stated once, in `configDefaults` (`schema.ts`), beside the schema that declares the key.** Two readers need it, `main.tsx` seeding a session signal and `write.ts` deciding whether a session value diverges from the file, and they each restated every default independently; a disagreement between those copies makes `ctrl-s` either decline to write a setting the user changed or write one they did not, and the structure guaranteed a fresh pair of copies for every key added. A `satisfies` clause checks the record against `UserConfig`, so a typo or a value the schema would reject is a compile error. Only keys whose absence _is_ a value belong there: `editor`/`ide`/`theme` are absent because unset means "nothing to say" and is deliberately never written, `sidebar.width` because an absent width is the responsive default `computeLayout` derives, and the registries because they are merge bases their resolvers fold over. The literals in `test/config-write.test.ts`'s `snapshot()` factory are what pin the record's values (a session at the defaults against a file omitting every key must write nothing), so they must stay stated independently there and never be sourced from `configDefaults`, which would make those cases agree with themselves and guard nothing. `loadConfigText` decodes each top-level key on its own, so a bad value costs only its section, and reports unknown keys (top-level and inside typed sections) by diffing raw keys against the decoded result; the pre-restructure flat `icons` glyphs get a pointed message naming their new location (`icons.glyphs`). A CLI flag wins over its config key for the run it was passed on (`--no-icons` and `--wrap` only ever turn a thing off, so flag-or-config composes). It loads on its own short-lived `ManagedRuntime.make(ConfigLive)` in `main.tsx` _before_ the app runtime's first use, because the active theme and file-support registry must be fixed before the diff highlighter warm-up reads them; a missing/invalid config falls back to defaults plus a notice and never blocks startup. `ctrl-s` is the one config write path: `state.persistSettings` snapshots the persistable session signals (exactly the ones the schema owns: theme, wrap, sidebar open/width/height/position/changes-only, search toggles, icons, plus the literal `--editor`/`--ide` flags via `editorFlag`/`ideFlag`, never the resolved templates, so an environment-derived editor is never frozen into the file and an absent flag never touches the key) and `Config.persistSettings` (`ConfigLive` is also in `AppLayer` for this) applies comment-preserving `jsonc-parser` edits through the pure `updateSettingsText` in `src/config/write.ts`, writing only keys that diverge from the file (theme keeps #113's pair rule: a picked name rewrites only the current appearance's half of a `{ dark, light }` pair, and `auto` removes the key). A document that fails to parse is never edited; the theme picker's own `ctrl-s` commits the previewed theme first so the session and the file land on the same value. `ctrl-s` saves everywhere, one key one meaning: the search pane's scope-picker chord is `ctrl-o` (moved off `ctrl-s` for exactly this reason), and its input-owning branch repeats the save dispatch since unmatched keys never fall through to the global branch. **A theme is a palette, and stet derives its UI from it, the cmux model.** Every theme is a Zed theme object (`ZedTheme`, `src/theme/zed.ts`), and `deriveTheme` (`src/theme/derive.ts`, pure and cached per object) computes the whole `Theme` token record from the background, the foreground, the six terminal hues (`terminal.ansi.red`/`green`/`yellow`/`blue`/`magenta`/`cyan`), and an optional `text.accent` (else magenta). Borders, text tiers, and the cursor row are fg-into-bg blends and the panel is the background darkened toward black, at fixed `STEPS` measured off stet's own palettes; kinds, stages, and severities are the terminal hues; file icons name a hue in `ICON_HUES`. So no theme ever names a stet role, any Zed theme is a complete stet theme, and code and chrome cannot disagree. Do not reintroduce per-role authored tokens, `base` merges, or a separate `syntax` theme: that is the structure this replaced, whose themes took ~80 hand-written colors and whose bundled `syntax` themes painted code over unrelated chrome. `normalizeTheme` runs once at registration, flattening alpha over the background and converting `color(display-p3 ...)` to sRGB hex, since the terminal, OpenTUI, and the diff's span parser take only `#rrggbb`. The built-ins (`src/theme/builtins.ts`) are palettes through `paletteTheme` (`src/theme/palette.ts`, which also maps a palette to Zed syntax scopes): `stet-*` (stet's own look), `opencode-*` and `cmux-*` (those tools' defaults), and `mono-*`. The registry (`src/theme/registry.ts`) adds the 75 themes bundled in `@pierre/highlights/themes/loader`, imported on demand (`loadTheme` awaits the active one before the first paint, `loadBundledThemes` imports the rest after it), user themes read from Zed theme files in `themesDir()` (`src/theme/user.ts`, `parseThemeFile`, one issue per bad file), and `system`, built by `src/theme/system.ts` from the terminal's own palette (`renderer.getPalette`, probed beside `waitForThemeMode` at startup and re-registered on the renderer's `palette` event, which OpenTUI emits after a mode flip). An undefined selection resolves to `system` when the terminal reported a full palette, else `stet-dark`/`stet-light` by appearance. Theme state is reactive (`src/theme/active.ts`, a `createRoot` of signals): `appearance` follows the terminal (updated live by the renderer's `theme_mode` event in `app.tsx`), `selection` is the config choice, `activeThemeName` is a memo over both, and `activeZedTheme` is the theme object behind it, compared by identity so a registry bump that leaves it unchanged (another bundled theme landing) wakes nothing. The `theme` handle (`src/theme/context.tsx`) is a stable object whose `colors`/`rgba` getters read the `activeTheme` memo, so call sites (which read `theme.colors.x` in JSX/thunks) re-theme with no change. The diff engine reads `activeZedTheme` (not `state`) and registers each theme object once under a fresh highlighter name, keying its highlight cache by that name, so a theme replaced behind the same stet name (a re-probed `system`) never serves stale colors; the diff and search effects in `state.ts`/`search-pane.tsx` re-run on `activeZedTheme`. The `t` theme switcher (`src/components/theme-combobox.tsx`, mirroring the `FileCombobox` overlay) writes the same `selection` signal live: `themeComboboxResults` (a filtered `themeComboboxItems` over `themeNames()`, with an `auto` row for the `undefined` selection) drives a preview effect in `state.ts` that re-themes the whole UI while the picker is open, fed by keys, hover (`onMouseOver`), and the wheel through one `themeComboboxIndex`; `closeThemePicker(commit)` either keeps the highlighted selection or restores the `themeComboboxOrigin` captured on open. `resolveFileSupportConfig` validates the `icons.glyphs` and `files` registries before both register in `main.tsx`. Same-name objects partially override built-ins, new names add entries, and `false` disables an entry. Invalid whole-entry overrides report issues while retaining the built-in; an unknown icon or syntax reference on a file association drops only that facet.
- Default file icon matching uses the public `createFileTreeIconResolver("complete")` from `@pierre/trees` in `src/file-support/icon-resolver.ts`. Trees answers for every name no built-in or user association claims; the adapter maps its tokens to terminal glyph/color names. Explicit `files` icon facets take precedence, preserving path globs, case-sensitive rules, and `false` as the generic icon. Syntax inference remains independent. Stet adds icon rules in two places, and which place a rule belongs in follows from precedence. A rule that must beat Trees (test and story globs over their language icon, ecosystem filenames like `package.json` and `Makefile` that Trees reads as JSON or nothing, and `.csv` over Trees' table icon) is a built-in `files` icon association. A rule that only fills a type Trees lacks (`.java`, `.toml`, `.lock`, an unknown dotfile as `config`) is in `icon-resolver.ts`'s fallback, which runs only when Trees returns its `default` token. Every association outranks Trees at any specificity, so an extension or dotfile rule there would shadow Trees' own filenames (`.lock` over `bun.lock`, dotfiles over `.gitignore`). A compound extension the single-extension fallback cannot express, such as `*.rb.tmpl`, is a narrow glob association, which shadows no Trees filename. Readme and license names are neither: they resolve in `icon-resolver.ts` only when Trees' token is `markdown` or `text`, or when Trees has none and no fallback extension claims the file (`License.java` stays Java), because Trees already tells a document from code named after one (`License.tsx` is `react`), while no filename glob tells `LICENSE-2.0` from `license-2.ts` or `README.zh-CN.md` from `Readme.tsx`. #389 dropped both kinds and left ~20 catalog glyphs unreachable; a glyph in `builtinIcons` with no rule that reaches it is a bug.
- File, folder, open-folder, and symlink glyphs are named entries in `src/file-support/builtins.ts`; user `icons.glyphs` extend or override the same catalog. They are on by default and gated by `state.iconsEnabled()`, seeded from `icons.enabled` and forced off by `--no-icons`. Every file-leaf icon renders through `src/components/file-icon.tsx`: a fixed 2-cell box that takes the full repo-relative path, self-gates, handles symlinks, and reads `theme.colors.icon[name]` with `text.muted` fallback. The tree, file picker, search, and binary preview all reuse it. Directory icons use the same named catalog and color map inline in `TreeRow`, preserving the disclosure triangle when icons are off. File-type icons take the terminal hue that suits them (`ICON_HUES` in `src/theme/derive.ts`), so they follow every theme's palette; structural and generic icons stay muted. Every colored icon must maintain at least `3:1` contrast against the base, panel, and cursor surfaces in `stet-dark` and `stet-light`. `test/theme-registry.test.ts` accounts for every built-in icon as colored or intentionally muted, so adding one requires an explicit palette decision.
- The header bar (`src/components/header-bar.tsx`) is scope-aware git identity on the left, view stats on the right, budgeted to `terminalWidth()` so it never clips. Left is context: in the main checkout `repo ─ branch` (repo = the stable `mainWorktreePath` basename), in a linked worktree `worktree-folder ─ branch` (the folder is the primary token, dropping the branch when it strictly equals the folder to avoid duplication), each with a leading Material Design Nerd Font glyph (`md-source_repository` U+F0CCF vs `md-file_tree` U+F0645) and an `md-source_branch` (U+F062C) glyph on the branch. Glyphs are decorative (icon-gated on `iconsEnabled`, dropped under `--no-icons` where the text carries the meaning), code points verbatim from glyphnames.json. A `commit` scope drops the identity entirely (a pinned commit is unrelated to HEAD's branch) and shows the full commit subject in the left slot spanning the width up to the right stats, truncating with an ellipsis only when it does not fit; the branch (non-commit) and subject (commit) are the flexible tokens the width budget shrinks first, then the primary name, then the scope label down to `MIN_SCOPE` while the primary name keeps `MIN_PRIMARY`, and never the changed count. The current branch rides live on `GitModel.branch`, parsed from the `##` header of `git status --porcelain=v1 -b -z` (`parseBranch` in `src/git/model.ts`), so it refreshes on the same drain as the changed set. The header carries **no live cue**, and should not grow one: an `N worktrees active` cue briefly shipped here and crowded the densest row in the app (joined by the same separator as the identity, it read as a third peer token beside repo and branch, and said only how many, never which). Worktree activity belongs to the picker, which answers the whole question.
- **Which worktree is an agent working in** is answered by git and filesystem activity, never by looking for the agent (agent integration is a v1 scope guardrail, and stet must work in any git repo). `src/git/worktree.ts` is the pure module (it owns `Worktree`/`parseWorktreeList`, moved out of `model.ts`, plus the activity model). A `WorktreeSummary` is just `lastActivityAt`: **the most recent of a changed file's mtime, the `logs/HEAD` reflog mtime, and HEAD's commit time.** All three are load-bearing. Uncommitted edits alone were the original model and were **actively wrong**: they drop to zero the instant an agent commits, so a just-finished agent's worktree ranked dead last. The reflog (a free `statSync`; the git dir is resolved without git from `<worktree>/.git`, and `git status` never rewrites it, unlike `index`) covers commits, checkouts, rebases, and the worktree's own creation; the commit time is the portable floor when reflogs are off, fetched for **every** worktree in one batched `git show -s --format='%H %ct' <shas>` since they share one object database. Every value is a real timestamp, not the moment we noticed, so a late poll still reports an exact age. `Git.worktreeSummaries` swallows a dead worktree to an omitted entry rather than failing the batch. A background fiber in `state` (keyed on `repoRoot`, `AbortController` + `onCleanup`, exactly like the refresh loop) re-summarizes every `PEER_SUMMARY_MS`; its `git worktree list` is also the discovery mechanism (an agent can create a worktree mid-session, so the list can't be resolved once at startup), and a single-worktree repo stops there and never pays for a `git status`. `mergeWorktreeSummaries` returns the previous map when nothing moved, so an idle repo's poll wakes no renderable.
- **A worktree stays active for `WORKTREE_ACTIVE_MS` (5 min), not the 30s `RECENT_MS` a changed file does**: an agent pauses for minutes at a time and is still working there, so the file-level window would grey out a worktree that is plainly still busy. The two windows coexist through one optional parameter, `recencyFraction(at, now, window = RECENT_MS)`; pass it wherever a worktree's recency renders, or the age fades out at 30s while the agent is still working. The picker (`WorktreeCombobox`) row is the branch, its badges, and **the age** (a `relativeTime` tinted on that ramp), with no changed-file count (a column repeating `clean` costs the branch name its cells to answer a question nobody asked) and **no per-row path** (a repo's worktrees share a long prefix, so a path truncated to a fixed column slices it at a different offset per row and cuts the leaf, the only part that differs). The highlighted worktree's full path gets its own row above the hint instead, where it fits complete. The **filter** follows the same reasoning as the row: a typed query is matched (case-insensitive subsequence) against the branch label plus the path's distinguishing tail (`worktreePathTails`, the segments after the prefix every worktree shares, compared segment-wise so a shared parent never slices a leaf mid-name), never the whole absolute path. The shared prefix is the same text in every entry, so as filter text it can only ever match all of them at once (`dev` matching every worktree through `/Developer/`) and never separate two; matching it also drags uncontrolled path characters into the haystack, which is what made the picker's filter test flaky (`branchzzz` matched a temp path whose random `mkdtemp` suffix happened to carry two more `z`s). The age, not a `RecencyDot`, carries recency in the row, because `●` already means "current worktree" there and one glyph must not carry two meanings (the word is the signal, so the row survives `NO_COLOR`). `orderWorktrees` sorts purely by recency with **no pin for main**, applied **once on open** so the list never reorders under the cursor while the cells stay live. Two layout rules there are load-bearing, each having already caused a bug: every cell is a **fixed-width box, never a padded string** (a whitespace-only `<text>` measures zero cells in a flex row and slides every column right of it out of line), and the width budget subtracts **four** cells from `overlayWidth` (two for the overlay's border, two for the row's padding; budgeting the padding alone overruns by exactly the border and the renderer silently clips it off the right edge). See SPEC's Worktrees section.
- A binary file renders a metadata surface, not raw bytes and not a blank pane: `src/components/binary-preview.tsx` centers the file type, image dimensions, and human-readable size (an old -> new delta in diff mode), the metadata an IDE shows for an image. stet does not draw image pixels yet, although OpenTUI ships an `<image>` element (Kitty, sixel, or block fallback). Dimensions come from `src/file/image-meta.ts` (`imageMeta`, a pure magic-byte header read for PNG/JPEG/GIF/WebP/BMP, no decode; SVG stays text), threaded through the enriched `binary` variants of `FileContent` (`src/file/content.ts`) and `SideContent` (`src/git/file-patch.ts`). Diff mode has no patch, so `git.binaryMeta` fetches both sides' `SideMeta` (reusing `fileDiffSides`/`fetchSide`) onto the `DiffView` snapshot's `binary` field; the `Viewer` gate prefers `BinaryPreview` over `DiffView` whenever a side is binary, in either view mode.
- Any surface showing a source line highlights it through the diff's shared `highlightSnippet` (`src/diff/engine.ts`), never plain text: the diff and the search results. The shared renderer is `src/components/code-line.tsx` (one `StyledText` buffer per line, clipped by its row), fed by a per-surface span cache that invalidates on new content or `activeThemeName()` and upgrades rows plain -> highlighted in place (identical text, no layout shift).
- Keybindings are data end to end in `src/keys/`: `actions.ts` is the canonical registry of rebindable actions (`{ id, context, combos }`, contexts `global`/`viewer`/`tree`, defaults written in the help's display style), `combo.ts` the pure grammar (`parseCombo`/`matchesKey`, which normalizes the terminal shift-letter ambiguity and matches modifiers exactly, so a bare combo never fires on a chord and the old per-site `!shift`/`!ctrl` guards are structural), `resolve.ts` merges `config.keybindings` over the defaults with issues (unknown id, bad combo, conflict; the chain order wins on conflicts), and `registry.ts` is the process-global set `main.tsx` registers. The keymap's global section and pane tails dispatch through `pressed(id)` at the same chain positions the inline conditions held; the modal overlay chain (pickers, menus, quit confirm, the search pane) and `ctrl+c` stay hardcoded, deliberately not rebindable. Help rows live in `src/help/keys.ts` (`keyHelpGroups()`), reference action ids, and render each action's current primary combo, so the `?` overlay, `stet --help`, and the generated docs (via `script/gen-docs-keys.ts`, which also emits the rebind ids) can never drift from what actually fires; add or edit a binding in `actions.ts` plus its help row, never in a renderer. The `?` overlay is two views toggled with `tab` (`state.helpView`): the keys, and a **marks legend** (`src/help/legend.ts`, `legendGroups()`) that explains the tree glyphs (change kinds, stage colors, recency). Like the keys, the legend reads each mark from the one place that draws it, `kindLetter`, so a mark and its meaning cannot drift; enum-keyed `Record`s in `legend.ts` make a new change kind or stage a compile error until it earns a row.
- Conventional commit style for commits and PR titles: `type(scope): summary`, with types `feat`/`fix`/`docs`/`chore`/`refactor`/`test` and an optional scope. Commits go through `bunx gitzy` (see "Implementing a change").
- No AI-generated sign-offs in commits, PR text, docs, or generated content.

## State and Effect conventions

This repository uses the Effect TypeScript library.

Before writing any Effect code, first read `node_modules/effect/AGENTS.md` **completely**, and follow the links in the file when required.

If you need to learn more about particular Effect apis and concepts that the guide doesn't cover, search through the source code in `node_modules/effect/src`.

Reactive state is SolidJS-native (signals/memos); async IO is Effect v4. `effect` is pinned to an exact version, so a bump is an explicit edit and its fallout lands in one reviewable change. The two layers meet only at one seam: the long-lived `ManagedRuntime` in `src/runtime.ts`.

- Wrap existing pure functions in services; do not rewrite the pure logic, so its tests stay intact.
- Define services with `Context.Service` plus a `Layer` (there is no `Effect.Service` in v4); define errors with `Data.TaggedError`, one tag per distinct failure, each in its own module beside the service that raises it (`clipboard/error.ts`, `config/read-error.ts`), since `max-classes-per-file` allows one class per file. Code is organized by domain folder under `src/` (`git/`, `file/`, `diff/`, `clipboard/`, `watcher/`): each colocates its pure modules with the Effect service that wraps them in a `service.ts`. The service `Layer`s are still assembled once into `ManagedRuntime.make(AppLayer)` in `src/runtime.ts` (the single assembly point); run service effects through `runtime.runPromise`/`runtime.runFork`, never with a fresh `Effect.runPromise` + `Layer.provide` per call.
- Prefer the data-last pipe form for combinators (`x.pipe(Effect.flatMap(f))`) over the data-first form (`Effect.flatMap(x, f)`); the two-argument data-first form trips `unicorn/no-array-method-this-argument`.
- All app state lives in `src/state.ts`: one global `createRoot` exposing `createSignal` primitives, `createMemo` derivations, and `createEffect`-driven async flows, exported as the `state` object. Components and the keymap import `state` and read accessors directly (`state.selectedPath()`), so reactivity is fine-grained: only the renderables whose inputs changed update. `App` owns the render-tree/renderer concerns `state` deliberately does not: keyboard wiring, terminal-dimension sync, and the deleted-worktree recovery effect (it calls `renderer.destroy()`). `main.tsx` seeds the signals (in one `batch`) before `render`. **The terminal title is the exception and is driven from `main.tsx`, not `App`**: it is a terminal control, and OpenTUI throws on a terminal control while the terminal is not active, which is every test renderer (`createTestRenderer()` skips terminal setup) and the real one while the terminal editor holds the screen. So its effect (`syncTerminalTitle` in `src/terminal-title.ts`) runs beside the renderer that set the terminal up, skips its write while `renderer.isDestroyed` or `state.terminalSuspended()` (which `openInEditor` raises before `suspend()` and clears after `resume()`), and re-runs when the suspension ends, so a title that changed meanwhile still lands. Destroying the renderer resets the title, so no exit path writes one.
- Async data flows are Solid effects that run an Effect through the runtime and write a signal: the diff/content pipeline is the load-critical one. The diff is rendered by stet's own windowed renderer (`src/diff/`, `src/components/diff/diff-view.tsx`) over `@pierre/diffs` (headless parse + `highlights`-backend highlight), not OpenTUI's built-in `<diff>` (whose gutter-width oscillation wedged the scheduler). `createEffect` keyed on the selection forks the load via `runtime.runPromise(effect, { signal })` and commits the `diffView` snapshot once, already highlighted (abort-guarded): the `highlights` backend tokenizes a 4k-line file in ~35ms, so the old plain-rows-then-highlight upgrade bought nothing. The previous snapshot is held until the new one resolves, so the renderer never receives empty/stale/partial content. Keep diff updates coherent and one-per-selection.
- Cancellation is via the `AbortController` passed to `runtime.runPromise`'s `signal` and `onCleanup` (Solid re-runs the effect on dependency change, aborting the prior — which interrupts the Process fiber and kills any in-flight git). Background fibers (the watcher and safety poll, the quiet re-run) follow the same restart-on-rekey pattern; aborting the controller closes the `fs.watch` handles via the watcher stream's finalizer.
- **Action placement.** A model/data action lives in `state` and is reached directly by components, the keymap, mouse handlers, and effects, never prop-drilled (placing one in `App` and threading it down was the `switchWorktree` bug). An action with an irreversible host side-effect (the `renderer` or `process`) is injected into the keymap through its `HostEffects` seam, and reached inside components via `useRenderer()` (as `useLineMeasurer` does). Never put the `renderer` in `state`: it is a render-tree resource, and keeping it out is what keeps `state` testable and the keymap's `quit` injectable.
- The keymap is `createKeyHandler(host)` (`host: HostEffects` carries only `quit`); it reads/writes `state` directly and wraps each dispatch in Solid `batch` so a keypress is one update. Mouse is wired symmetrically: handlers dispatch into the same `state` signals, each in `batch`, so a click mirrors the equivalent key. In `DiffView`, one stable viewport overlay owns click, wheel, and drag input; never attach viewer mouse capture to a windowed row that may unmount as the visible slice changes. Every action except `quit` lives in `state` (including `switchWorktree`, so the keymap, the worktree picker's click, and App's recovery effect all reach it directly). `quit` exits through `exitAfterRestore` (`src/shutdown.ts`), the one exit path once the renderer is up: it calls `renderer.destroy()`, awaits `renderer.closed`, then logs any message and calls `process.exit`. `destroy()` returns at once but restores the terminal asynchronously, and `closed` resolves once the restore is written, so the message lands on the restored screen rather than the alt buffer and the exit cannot cut the restore short. A rejected `closed` (the output failed, or the close ran late) leaves nothing stet can still restore, so it exits the same way. The background poll keeps the event loop alive otherwise. Every quit trigger routes through this one `quit`: `q`/`esc` and ctrl-c alike, and the keyboard path additionally prints the post-exit "new release available" notice, but only when the background check found a newer release (the worktree-recovery exit calls `quit` without it, and the OS-signal/crash backstops never route here, so both stay silent). `q` does not quit directly: it opens the `quitConfirmOpen` alert dialog (`quit-confirm.tsx`, an early keymap guard) that only calls `quit` on `y`/`enter`, so no single keystroke ends the app; `esc` never quits (it only ever closes the search view), and ctrl-c stays instant (checked before the confirm guard) as the deliberate escape hatch. `QuitConfirm` is stet's one true **modal**, distinct from the dismissible picker/palette overlays (help, comboboxes, scope/command menus): an alert dialog is a decision surface, so it renders a full-screen barrier that dims the app with `surface.scrim` (an opaque theme token blended to a fixed alpha in `resolve.ts` as `rgba.scrim`) and captures background mouse-down, keeping the app inert and never dismissing on an outside click (the alert-vs-dialog line). The pickers stay casually dismissible and add no barrier, because they are browsing surfaces, not decisions. `render` sets `exitOnCtrlC: false` and the keymap handles ctrl-c itself, because OpenTUI's built-in `exitOnCtrlC` only calls `destroy()` (never `process.exit`), so it hangs behind the poll instead of exiting. An OS-signal backstop in `main.tsx` (`exitOnSignals` in `src/shutdown.ts` for `SIGINT`/`SIGTERM`/`SIGQUIT`/`SIGABRT`/`SIGHUP`/`SIGPIPE`, plus `main.tsx`'s own `uncaughtException`/`unhandledRejection` handlers; `exitOnSignals` takes the still-pending `createCliRenderer` promise, because the renderer enters the alt screen before it resolves and a signal in that window would otherwise take its default action and skip every restore) restores the terminal through the same `exitAfterRestore`, a signal exiting with the shell's 128 + signal number and a crash with 1, even when a wedged input loop never delivers a keyboard quit, so an external kill or a crash can't leave the alt-screen buffer active and the next launch blank; `renderer.destroy()` is idempotent, so the backstop composes with the keymap's own `quit`. **stet owns shutdown, so the renderer is created with `exitSignals: []`.** OpenTUI's default handlers only call `destroy()`, and a listener replaces a signal's default termination, so with them installed a signal stet did not also handle restored the terminal and left the process running behind the poll. The backstop therefore covers the list those defaults did, minus `SIGBUS` and Windows-only `SIGBREAK`: a real bus error cannot be handled from JS (the faulting access repeats, so a listener spins at full CPU in the alt screen), so it is left to crash. **An output failure is the one shutdown no signal announces**: since OpenTUI 0.6 an output stream that errors, closes, or finishes makes the renderer destroy itself and reject `closed`, so `main.tsx` also runs `exitOnOutputFailure`, which exits with code 1 unless stet started that shutdown itself (tracked per renderer in a `WeakSet`, so a test renderer never carries the mark into the next test). Without it the git poll keeps a process with no screen alive (`test/shutdown.test.ts`).
- **The main area is a view mode, not a stack of booleans.** `mainView` in `state` is a union (`"file" | "search"`) rendered by a `Switch` inside the `Viewer`, so exactly one view ever owns the pane interior; a future pane extends the union, adds a `Match`, and gets a keymap branch, never another `xOpen` flag with implicit precedence. View-local state (the search pane's query/results/selection) lives in its own signals and simply persists when `mainView` returns to `"file"`, which is how close-and-reopen restores the pane for free. `focusedPane` carries a matching value (`"search"`) so the keymap's modal chain and the search view's focus marks react to it like any pane.
- **Viewer navigation uses one history.** The pure model in `src/viewer/navigation.ts` stores an ordered list of `Location`s, the current index, and the last position per file. `state` renders from the live signals and captures them on leave through `captureCurrent` and `recordLeaving`. The `Viewer` effect consumes `pendingRestore` once the diff loads under the matching view intent. If the user leaves before that restore finishes, capture saves the pending request with the history entry and the remembered file position. A new navigation replaces the active request. A settled cursor is stored as a file line and diff side; a search jump's column only scrolls the match into view. See SPEC's Viewer navigation section.
- **The viewer's selection is a transient pair of glyphs, owned by stet.** `viewerSelection` (`Selection` in `src/viewer/selection.ts`: anchor, focus, and a `character`/`word`/`line` unit) is set through `select`, which puts the cursor on the focus line, and cleared through `clearSelection` by every plain cursor move (`setCursorRow`), every navigation (`goToLocation`, the one choke point), and `esc` ahead of the global one. It is never captured into navigation history. Its endpoints are row indices, so whatever replaces `navigableLines` must move it: a fold or gap toggle does (`remapSelection`), and an effect moves it across a refresh (`followLines`), where a drag in progress takes its anchor from it. `selectionRange` derives the span, and the text, painted columns, and reference lines derive from that; a folded/git-elided region is excluded for free since it never enters `navigableLines`. **The release copies** (`finishDrag`), once: OpenTUI reports both a drag's end and the button going up, and unmounting only cancels. A whole-line selection reuses the cursor lift in `DiffView`'s `resolveBackground`; any other paints `selection.bg` on its own columns, and a row holding selected text drops the lift from its code while its gutter keeps it (`isCodeLifted`), since a lifted add/remove row sits too close to `selection.bg` to show where the selection ends and the gutter still marks the caret line. A single transparent, absolute interaction layer over the viewer owns click, wheel, and drag input; never put mouse capture back on a windowed row, because the captured renderable can unmount as the visible slice changes. A press is one batch (`pressAt`), and the context menu opens after it, since moving the cursor can scroll and the menu closes on a scroll it did not open at. Every press closes an open context menu, since a press on the caret's own line drifts nothing the menu's guard watches. The line row's **text leaves** set `selectable={false}`: OpenTUI starts its own native text selection on the deepest selectable renderable a left-drag hits, and its selection would lose rows as they unmount. `pointAt` is the one mapping from a pointer to a glyph, through the cumulative measured row heights and `cellWidth`, so it stays exact in scroll and wrap modes; a marker row resolves to the line on the drag's own side. Holding a drag past the top or bottom of the viewport (never on its first or last row, which a drag there is selecting), or at its left or right edge, runs one 50ms timer that scrolls (a row vertically, `HORIZONTAL_STEP` sideways in scroll mode, except for whole lines) and extends to the pointer on each tick; returning to the interior, releasing, unmounting, or reaching the end stops it. Cursor-follow margins stay suspended for the full mouse press so they cannot accelerate or fight that timer. Drag, not shift-click, is the portable mouse range gesture: many terminals reserve `Shift+mouse` for their own text selection and never forward it. Actions live in `state`, reached by keymap/mouse like every other.
- **Text outside the viewer uses OpenTUI's native selection**, copied by `App`'s listener on the renderer's `selection` event, and colored by `renderer.setSelectionColors`, which `App` keeps on `selection.bg` (the viewer's own) under `text.primary`: the faint and muted tiers sit too close to that background to read on it. Any text leaf inside a row that acts on a click sets `selectable={false}` on the `<text>` itself (OpenTUI hit-tests the leaf, so the parent box's flag does nothing), as do decorative glyphs, the scrollbar, and the bars' backdrop rules (a separator between fields, like `BAR_SEP`, stays selectable, since it keeps the fields apart in copied text); `test/native-selection.render.test.tsx` guards the rows. Native selection joins texts on one row with nothing between them, so adjacent columns carry their own separating space (`HelpDialog`, the viewer title).
- **Folding and gap expansion are one "collapsed regions" seam.** `src/diff/regions.ts` is a pure module (no Solid/Effect/OpenTUI, unit-tested like `git/tree`): `foldRegionsFor` dispatches the region model on the file's language (`computeFoldRegions` indent-based for code, `computeMarkdownFoldRegions` heading-based for markdown; `state` derives the mode from `languageForPath`), and `applyCollapsedRegions` rewrites the row stream for the current fold state, emitting a non-navigable `marker` row (in the `DiffRow` union) for each folded block and **re-densifying each surviving line row's `navIndex` while rebuilding `navigable`**. Gaps are the diff engine's half of the seam: `@pierre/diffs`' `DiffHunksRenderer` lays out the rows for a set of expanded gaps, and `rowsFromHunks` (`src/diff/rows.ts`) turns its row stream into `DiffRow`s, a collapsed gap as a `gap:<hunk index>` marker and a revealed one as its lines (already highlighted) behind an open "hide" marker. A gap is expandable only when the diff carries both files' full text: `Git.fileDiff` returns a `DiffInput` that is either both files (the in-process path, which `parseDiffFromFile` turns into a full, non-partial diff) or git's patch alone; a git fallback patch keeps plain `separator` rows, because textconv and clean filters can renumber its lines, so raw bytes beside it would fill its gaps with the wrong text. That re-densification is the load-bearing invariant: the caret (`cursorIndex`) indexes only visible lines, so it can never land inside a fold. `state` holds two `Set`s with opposite defaults (`foldedRegions` present = collapsed, `expandedGaps` present = expanded). The renderer lives in the render's own closure, never in `state`: `DiffRender.expand(gaps)` re-lays out its cached whole-file highlight synchronously (~1ms), so `expandedLayout` (the memo over `expandedGaps`) and the purely computed next navigable a toggle remaps against both call it in the same batch; `collapsedRender` folds that layout and feeds both `navigableLines` and the viewer's rows, keyed on the fold/gap sets (not the caret, so cursor moves don't recompute it). `truncated`/`truncatedHidden` stay on the raw `render` (the maxLines cap is about the whole file, not what the user folded). Toggle actions (`toggleFold`/`toggleGap`/`toggleRegionAtCaret`, reached by keymap/mouse like every other action) remap the caret against the next navigable computed purely in the same batch (`remapCursorAfterToggle`), and `revealLineForJump` clears a fold covering a jump target so jumps still land. The viewer keeps a jump pending while it reveals a fold or loads full content. Keys: `z` folds/unfolds/expands at the caret (wrap moved to `x`).
- **The context menu is a thin dispatcher, shared across two panes.** Right-click (a tree row or a viewer line) or `Shift+F10` opens a menu whose items only dispatch existing self-guarding `state` actions; it introduces no new behavior. The item list is a pure model (`src/components/command-menu/items.ts`, `buildCommandMenuItems`, unit-tested like `viewer/anchor.ts`) that `state.commandMenuItems` wraps over the live caret/tree signals, so the render and the dispatch (keymap `return` and row click) read the same list and the highlighted index always maps to one action. One presentational `src/components/command-menu.tsx` renders it, placed by `placeCard` (`src/viewer/anchor.ts`) in two coordinate frames: the viewer instance mounts **inside `DiffView`** and anchors at the right-clicked cell, or at the start of the caret line from the keyboard; the tree instance mounts in `App` and anchors in global terminal coordinates at the clicked/`focusedRow` cell. Shared `commandMenuOpen`/`commandMenuIndex`/`commandMenuContext`/`commandMenuAnchor` signals (only one instance is ever open) gate a keymap modal block placed right after the scope-menu block, so it owns the keyboard while open. Right-click is detected by `event.button` through `isRightClick` (`src/components/mouse.ts`, the one place that reconciles OpenTUI's `number` button with `MouseButton.RIGHT`); a right-press focuses the node/caret (or keeps a selection it lands in) then opens the menu, a left-press keeps today's behavior. Every item dispatches through `state.dispatchCommandAction` except `openEditor`, which needs the renderer: `src/editor/open.ts` holds the shared `openInEditor`, reached by the keymap's `HostEffects` (App wraps it with its renderer) and by the menu's row click (via `useRenderer()`), so the renderer is never prop-drilled. Opening captures a `commandMenuGuard` snapshot (pane, file, focused node, caret, scroll, scope, repo) and a clear effect `closeCommandMenu()`s the instant any of it drifts: this is the invariant that keeps "menu open" from outliving the anchored render (a click elsewhere moves the caret/focus and dismisses the menu, so it can never linger invisibly and swallow keys). Inapplicable actions are omitted from the list rather than shown disabled (Copy selection only with a selection, Show full content only when the file is truncated; a directory offers just Copy path), so every visible row acts; the highlighted row carries a `▸` caret so the selection reads under `NO_COLOR`.
- **stet owns focus, so disable OpenTUI's.** The renderer is created with `autoFocus: false` (`src/main.tsx`) so a click never native-focuses a renderable, which would draw the terminal cursor in it; an `App` effect hides the cursor whenever no overlay input is open (overlay inputs show their own caret via the explicit `focused` prop).
- **Long lists window to the viewport; never mount one renderable per row.** The sidebar tree and the search results render only their visible slice (`sidebarScrollTop`/`searchScrollTop` plus the viewport height) through `<Index>` in a plain box, with uniform height-1 rows. OpenTUI materializes native buffers per mounted element and `viewportCulling` only skips paint, so an unwindowed list rebuilt each refresh tick (fresh row objects through a reference-keyed `<For>`) stalls per tick and eventually exhausts native buffers on large repos. Cursor-follow lives in `state` (`followScrollTop`, margin 2), tracking only the cursor and viewport and reading rows/offset untracked, so a background refresh never snaps a wheel-scrolled window back to the cursor; a clamp effect bounds the window when the row list shrinks. Windowed row components read everything through props (an `<Index>` slot swaps its row in place, and can flip type) and set no renderable `id` (a per-slot changing id confuses the reconciler's anchoring). Every inline `<text>` leaf in a height-1 windowed row sets `wrapMode="none"`, since OpenTUI's `<text>` defaults to `wrapMode="word"` and a name or badge wider than its flex slot would break off at a word. **No text scrolls itself:** OpenTUI's `<text>` takes a wheel event before it bubbles and scrolls its own buffer whenever its content overflows its box, on either axis, so a wheel over a clipped or wrapped row left it painting the middle of its text. `src/components/static-text.ts` registers a subclass that stays put as stet's `<text>`, which is the one fix for every row; do not work around it per row (`test/static-text.render.test.tsx` and `test/sidebar-name-wrap.render.test.tsx` guard it). A label beside text that clips (a gutter, a sha) sets `flexShrink={0}`, or flex takes the overflow out of both. Per-row derived data must be O(1) lookups into precomputed per-directory maps (`directoryRecencyByPath`), never per-row scans over a whole map. The shared glue is extracted: a new windowed surface reuses `windowWheelHandler` (`src/components/wheel.ts`) for its wheel handler, `followListWindow` (local to `state.ts`) for the follow/clamp effect pair, and `ListScrollbar` (`src/components/list-scrollbar.tsx`) for the scrollbar, rather than copying any of them; the search pane's follow stays action-driven (`setSearchSelection`) by design, and DiffView's variable-height windowing (`visibleWindow`) stays bespoke. A windowed list mounts only its visible slice, so OpenTUI's native `<scrollbox>` thumb has no real content to measure (#187 lost it that way): `ListScrollbar` drives OpenTUI's `SliderRenderable` from the same `(rowCount, viewport, scrollTop)` the window already tracks, in a reserved width-1 column that stays when the content fits so growth never shifts layout. Solid has no element for it, so it is constructed in the component. Not the `ScrollBarRenderable` that wraps that slider: it sizes the thumb against the range of the moment, so a list whose rows arrive after its pane keeps a half-cell thumb. The slider reports every value change through `onChange`, so only a change made outside the list's own writes (a drag, a track click) moves the list. It also keeps every press to itself, whatever the button, so a subclass hands a press to the pane first (which focuses it) and takes only the left one. DiffView shows no scrollbar and has no scrollbox: its slice is one absolute column at `window().top - scrollTop()` inside a clipped box, so the mounted rows and where they paint come from one signal and no spacer or overscan stands in for the rest. Long lines scroll the same way, each at `left={-scrollX}` in a clipped box; never `scrollX` on the text, which clamps to that line's own length and shifts short lines out of their columns. A native `<scrollbox>` + `scrollChildIntoView` is no substitute: that imperative scroll-follow was unreliable in the full app (its computed delta depends on render/layout timing under `viewportCulling`, so the selection moved but the viewport never followed), while a windowed slice derived from a scroll-top signal is declarative.
- **Terminal dimensions become pane geometry in exactly one place, `computeLayout` in `src/layout/regions.ts`** (pure, no Solid/Effect/OpenTUI, unit-tested like `viewer/anchor.ts`). It partitions the terminal into the header row, the tree, the viewer, and the status row, returning each as a `{ x, y, width, height }` plus the `content` rect it may paint (the viewer's whole rect; the tree's minus the one cell its divider takes); `state.layout` is the thin memo over it and `app.tsx` places every region absolutely at the rect it returned, so nothing in the render tree computes a position or a size. **No renderer re-derives a budget from `terminalWidth()`/`terminalHeight()`**, and the enforcement is structural rather than a review habit: `state.sidebarWidth` and `state.paneHeight` were deleted, so the old `terminalWidth() - sidebarWidth() - N` shape (which lived in `DiffView`, `SearchPane`, and `TreeRow`, each with its own constant) is no longer typeable. That drift is what pinned the tree context menu's anchor to a hardcoded column. The model stops at the pane's rect: chrome a pane owns inside its own rect stays local (the viewer's title row and truncation footer, the search view's four chrome rows, a `TreeRow`'s padding), which is why the residual subtractions are small and sit at their call sites. The tree carves off its edge (`Dock`) and the viewer takes the rest. The edge comes from `sidebarPosition`, so `DOCKS` in `regions.ts` is the one list: `Dock` derives from it and `config/schema.ts` builds its `Schema.Literals` from it, which is why the type, the `d` rotation, and the schema cannot drift apart. Zoom is a model **input**, never a mutation of the open flag, so restoring is just clearing it and no key pressed while zoomed can strand a stale flag. It **follows focus** (`zoomed` is one boolean; `state` maps `focusedPane` to the model's zoom target), so `tab` moves which pane fills the band with no rule of its own. That map carries no open-flag check, and must not grow one back: it briefly did, as a patch for `switch-pane` focusing the tree whether or not the tree was open, and the fix belongs upstream where focus is chosen, not downstream where it is painted. The line that keeps it coherent: **an action that changes pane visibility exits zoom (`toggleSidebar`), one that only moves focus carries it**, and every geometry key (`[`/`]`/`\`/`d`) is inert while zoomed, since `zoom` does not close the hidden tree and a write there would land invisibly behind it.
- Tree resizing writes **one overridable signal per axis** (`sidebarWidthOverride`/`sidebarHeightOverride`): keyboard `[`/`]` nudge the tree along its dock axis and `\` resets **only that axis** to `null` (the layout model's default). Axis, step (2 columns or 1 row), minimum, and which override applies all come from the tree's current edge, resolved once in `sizingAxis` so `nudgePane`/`resetPane` share one code path for all four edges; `d` (`move-pane`) rotates the tree clockwise. Keeping a size per axis is the semantics, not just the storage: a move never converts columns into rows, and an axis returned to restores what was set there. The override is stored raw and clamped only inside `computeLayout`, so a manual size never overflows a shrunken terminal yet is restored when the terminal grows back, and the same clamp holds the viewer's `VIEWER_MIN_WIDTH`/`VIEWER_MIN_HEIGHT` floor. When the terminal cannot afford both minimums at once, the tree falls back to its own and takes what is there. Shrinking past the minimum collapses the sidebar (like an IDE pane) rather than clamping, moving focus off the tree the way the `ctrl-b` toggle does. Growing (`]`) a collapsed sidebar re-opens it to its remembered width, the inverse of that shrink; the reopen lives in `nudgePane` (a grow while closed), and `[`/`\`/`d` stay no-ops while collapsed because each self-guards on the tree's open state rather than on a keymap gate, so `\` never discards the width `]` reopens at. **The tree is the one sizable pane**; the viewer is whatever the dock leaves, so it has no size of its own and the keys act on the tree from it too. The action ids are `grow-pane`/`shrink-pane`/`reset-pane`/`move-pane`; the `*-pane` names date from when a second pane was sizable, and a rebind against the older `*-sidebar` ids carries a `renamedIds` migration notice so it names its destination instead of reading as a typo. **`focusedPane` never names a pane that is closed**, which is the invariant the zoom target, the keymap's unguarded tree tail, and every focus mark lean on. It holds because every writer either targets the viewer (always present), sits on the tree while it is mounted, or routes through **`focusNextPane`** (`tab`, which lands on the tree only while it is open) or **`collapseSidebar`**, the one close path shared by the toggle and a shrink past the minimum. `switchWorktree` seeds the new worktree's focus the same way (after `seedNav`, whose `closeSearch` a batched read must see settled), and `main.tsx` calls `collapseSidebar` rather than copying the rule, so the viewer's focus value lives once in `viewerFocus`. Open, not painted, is what `tab` tests, because zoom hides the tree without closing it and `tab` carries the zoom along. The search view keeps `tab` for its own three fields and the switch never starts there.
- Every subprocess runs through the `Process` service (`src/process.ts`, with its `CommandError` in `src/command-error.ts`, the one cross-cutting infra module that sits at the root rather than in a domain folder), an interruptible `Effect.acquireUseRelease` over `Bun.spawn` whose release kills the child; the git and file services and the startup load all compose it. There is no synchronous `Bun.spawnSync` path. **No git child writes the real index or takes `.git/index.lock`**, so a read never collides with an agent's commit and git reads do not retry. `Process` gives every child `GIT_OPTIONAL_LOCKS=0` (which stops `git status` from refreshing the index) and `diff.autoRefreshIndex=false` through `GIT_CONFIG_*` (porcelain `git diff` refreshes the index after a stat-only change whatever `GIT_OPTIONAL_LOCKS` says). Turning the refresh off also turns off git's own content check for stat-only changes, so the reads that need it (`changedFiles`/`loadModel`, the `fileDiff` pathspec fallback, the worktree summaries' `status`) run against a **private copy of the worktree's index** instead (`src/git/private-index.ts`, laid over the defaults through `Process.run`'s `env`) with the refresh on and `core.splitIndex=false`, after a `git update-index -q --refresh` against the copy: git then drops stat-only changes exactly, binaries included (`--numstat` prints a binary pair whatever its content, so no output-side filter can), and hashes a stat-dirty file once instead of every tick. Each rule there is load-bearing and tested: optional locks stay **off** even for the copy (git runs a nested `git status` inside each submodule with `GIT_INDEX_FILE` unset but `GIT_OPTIONAL_LOCKS` inherited, so turning them on rewrote the submodule's real index; `update-index --refresh` is what persists the copy's stats, writing only `GIT_INDEX_FILE` and comparing a submodule by its HEAD), the copy keeps the real index's mtime (git judges racily clean entries against the index file's own mtime, and a copy stamped now hid a same-second edit after `git add`), a split index must not be written back split (that creates `sharedindex.*` files in the real git dir), the copy is retaken under a fresh name whenever the real index's inode, size, mtime, or ctime moves (so a late git child refreshes the old copy, not the new one), and a copy goes when its index does. The real index is `<git dir>/index`, found without git by `gitDirOf` (`Process` strips any inherited `GIT_INDEX_FILE`). The copies live in a per-process temp directory that the Git layer's finalizer or the `exit` hook removes; `bun test` fires no `exit`, so the test preload disposes the app runtime in `afterAll`. **Exception:** `src/editor/service.ts` (`EditorLive`) spawns directly via `Bun.spawn` without the `Process` service. `Process` pipes stdio and kills children on fiber interruption; for a terminal editor that needs inherited stdio and for a GUI IDE that should outlive the fiber, both behaviors are wrong. `openTerminal` inherits stdio and awaits `proc.exited`, suspending the renderer around it; `openIde` ignores stdio and awaits exit to surface a non-zero code. `openExternal` (the OS default app, `open`/`xdg-open` via the pure `openExternalCommand`) shares `openIde`'s detached fork-and-forget spawn, so it needs no renderer and lives as the plain `state.openExternally` action (`O`, or the command menu's `openExternal`), reached directly like every other data action. The same exception covers `src/upgrade/run.ts`: `stet upgrade` is a pre-TUI one-shot path (like `--help`/`--version`, dispatched by `parseCommand` in `src/cli.ts` before the renderer or any runtime is built) that classifies the install method from `process.execPath` and spawns the right channel's update (`install.sh` re-run, `npm`, or `brew`) with inherited stdio so the user sees its progress live, so it uses `Bun.spawn` directly and needs no Effect/`AppLayer`. No other domain may bypass `Process`. Version awareness lives in the same domain as a plain (non-Effect) module, `src/upgrade/release.ts`: GitHub Releases is the canonical source all channels derive from (`tag_name`, stripping the release-please `stet-v` component prefix down to the bare version), read with a plain `fetch` (a `User-Agent` header is required or GitHub returns 403) bounded by `AbortSignal.timeout` and swallowing every failure to `undefined`. There is **no cache, no env opt-out, and deliberately no `service.ts`** here, the same AppLayer-free rationale as `run.ts`: no AppLayer dependency, no `Process` child, no fiber-interruption resource to model. `upgrade` short-circuits with `stet X is already up to date` when `fetchLatestVersion` resolves a version that is not newer, and falls through to the channel update when the check fails. `state.checkForUpdate` runs the same check in the background on launch (non-blocking, independent of the git load) and stores a hit in `availableUpdate`.

## Code design

- **Extraction is a design decision, not a refactor.** When you see duplication, surface it and propose. Do not extract shared helpers, types, or components unprompted, regardless of usage count. Whether two similar blocks are one concept or two is a judgment you don't have the context to make alone.
- **Inline by default; extract only when it earns a name.** Don't pull out single-use helpers preemptively: inline at the call site unless the helper is reused, hides a genuinely complex boundary, or has a clear independent name that improves the caller. When a function grows several branches, let the main function read as the happy path and move supporting detail into small named helpers (`requireConfig`, `readMetadata`) kept just above it (functions are `const` arrow expressions, which are not hoisted, and `no-use-before-define` enforces the order).
- **No speculative generality.** Don't add config options, generic parameters, or extension points for use cases that don't exist yet. The right abstraction for a future need is almost never the one you'd guess before seeing it.
- **Duplication is cheaper than the wrong abstraction.** Code that looks similar isn't necessarily the same thing. Deduping two unrelated pieces couples their futures; when one needs to change and the other doesn't, the abstraction has to grow conditionals or split back apart, both of which are worse than having kept them separate.

## Testing

- **Test behavior, not implementation.** Assert what a caller or user observes, not how the code achieves it. "Caller" and "user" scale with the unit under test: for a component it's the person clicking, for a function it's the code calling it. Tests that assert internals break on every refactor and prove nothing about whether the code works.
- **Prefer clarity over DRY in tests.** Inline setup, repeat literals, skip shared fixtures when they'd obscure the case under test. A test's job is to be readable in isolation; the pull toward DRY that makes production code better usually makes tests worse.
- **Test real behavior, not hypothetical behavior.** Cover the cases the contract actually promises. Do not manufacture edge cases the code doesn't claim to handle just to pad coverage.
- **Avoid mocks.** Test the actual implementation; reach for a mock only when a real dependency is genuinely unavailable, and never duplicate the code's own logic into the test.
- **A test never exits the runner.** `test/setup.ts` replaces `process.exit` with a throwing function, so reaching a production exit path fails the active test and Bun always prints its suite summary.
- **No test inherits another's state, however the previous one ended.** Bun runs every test file in one process, so the `state` singleton outlives each file, and a test killed by a timeout or a failed assertion never reaches its own cleanup. The preload registers a `beforeEach` that calls `state.resetState()`, so every test starts from the defaults without any test having to undo itself. The same `beforeEach` restores the theme, keybinding, and file-support registries to their defaults, clears the clipboard registry, resets the cell width method, puts back the bundled theme loaders from `@pierre/highlights/themes/loader` (a test may swap one to make an import fail), and resets the active theme's selection and appearance, since all of them live outside `state` (module-level state in `src/theme/registry.ts`, `src/keys/registry.ts`, `src/file-support/registry.ts`, `src/clipboard/registry.ts`, and `src/diff/cells.ts`, and `src/theme/active.ts`'s root) where `resetState` cannot reach them. A new process-global registry gets its reset there too, never a per-test `finally`. The preload's `afterEach` also removes every `createFixtureRepo` directory, so a test need not remove its own fixture repository. `resetState` is drift-proof by construction: inside `createState`, every signal is created through the local `tracked` helper, which records how to restore that signal's initial value, so a signal added later is reset for free. A signal is not the only thing that outlives a test, so each async guard (an in-flight `AbortController`, a pending timer, a staleness token, a "what we last loaded for" marker) passes its own teardown to `onReset` **beside its declaration**, never as a list inside `resetState`. Staleness tokens are **bumped, not zeroed**: they are only compared for equality, so restoring `0` would let an in-flight reply that captured `1` match the next `1` and be accepted as current. Never replace this with a hand-maintained reset list, and never rely on a test's own cleanup for isolation: a toggle leaked from one dead render test once took over the status bar for every file after it and turned one failure into fifteen. `test/state-isolation.test.ts` guards the invariant.

## Writing

- **No em dashes.** Use a comma, period, or restructure the sentence instead.
- **No horizontal rules as section dividers.** Don't use `---` to separate sections when a heading is already doing that job. Exception: `---` is fine as a thematic break when there is no heading on either side.
- **No curly/smart quotes in prose.** Use straight quotes (`"`) not curly quotes. Applies to prose only; code blocks are verbatim and exempt.
- **Sentence case subheadings.** Write `## Like this` not `## Like This`. Exception: proper nouns and acronyms follow their standard casing.

## Docs

- **After introducing a new pattern, feature, convention, or structural change, ask whether `AGENTS.md`, the repo-root `README.md`, and/or the docs site (`docs/content`) should be updated, then apply the changes.** Docs rot the moment the code moves without them. Catching the update at the point of change is the only time it reliably happens. For the docs site, `docs/AGENTS.md` maps each code area to the page that owns the facts it drives.
- **New or reworked UI surfaces clear the bar in `TASTE.md`:** design every state (default/hover/focus/active/disabled/loading/error), empty states included; theme tokens only; no layout shift; keyboard-operable; severity paired with its glyph; plain sentence-case copy.

## Implementing a change

- **Always work in a git worktree**, one branch per change; never commit directly on the default branch. Worktrees live under `.claude/worktrees/`.
- **Commit with `bunx gitzy`** (the project's conventional-commit prompt) rather than a raw `git commit -m`. It produces the `type(scope): summary` format with a leading gitmoji.
- **Keep the emoji**, and never add a co-author or AI sign-off trailer to commits.
- **PR description uses two sections and nothing else:**

  ```markdown
  ## What

  <what changed, in plain terms>

  ## Why

  <the problem or need it addresses>
  ```

  No trailing "generated by" / AI-attribution line, in the PR body or anywhere else.

## Deciding what to do

Judge every piece of work by whether it **should** be done (is it correct, is the current state wrong or inconsistent, does it serve the goal), and **never by ROI, cost, effort, or "is it worth it."** Do not label a known-wrong thing "low-value," "marginal," "an edge case," or "not worth it" to justify leaving it unfixed; reasoning by ROI is exactly what keeps work mediocre. ("The reference / competitor also gets it wrong" is a _gap_ argument, not a correctness one; it never makes a wrong thing acceptable.)

The only valid reason to stop short of doing the right thing is that it **provably cannot** be done: a demonstrated limit of the model or tools, not an assumed or cost-based one. "Hard," "heavy," "expensive," or "a lot of work" is never a reason to stop; "proven impossible / blocked" is. When unsure which it is, find out (try it, measure it, prove it) before deciding, and never declare a limit you have not proven.

Present choices by correctness and feasibility (real impossibilities, real _capability_ tradeoffs like portability or expressiveness), not by ROI.

## Fixing bugs

Assume a correct architecture has no bugs, so every bug is evidence that the architecture _permits_ it to exist, not merely that one code path is wrong. **Before fixing any bug, first diagnose the root cause: ask why the architecture allowed this bug to exist at all,** and whether it is one instance of a whole _class_ of bugs the same structure would keep producing.

Prefer fixes that remove the structural condition that let the bug exist, so this bug and others like it can no longer occur, over patches at the symptom layer (a guard, a special case, or a workaround that leaves the enabling structure in place). Reach for a symptom-layer patch only when the root-cause fix is **provably** infeasible or genuinely belongs in a separate change, never merely because it is larger or harder; when you do, say so and name the root cause you are deferring.

This is a thinking-first rule, not a mandate to refactor on every fix: the root-cause analysis is **always** required; reshaping the architecture to act on it is frequent but conditional on its being the right and feasible move.

## Pausing

- **Between phases:** after completing a discrete chunk of work, stop. Post a short summary, then ask before starting the next.
- **On uncertainty:** if a decision is not covered by existing rules or context, do not invent. Stop and ask.
- **On a debug loop:** if the same error persists after 3 consecutive fix attempts, stop. Report the error, what was tried, and the likely cause. Do not attempt a fourth fix without input.

## Scope guardrails (v1)

Do not implement a web preview, PR workflow, accept/reject protocol, agent integration, or a database. The tool must work in any git repo, not only this one or agent-created worktrees. There is no language server client: code intelligence and diagnostics were both removed to keep stet to git inspection, so bringing either back is a scope decision, not an increment.
