# stet: implementation spec

The repo-root `README.md` is the source of truth for what stet does, its keys, and its non-goals. This file holds the invariants behind those features, the contract the README doesn't state. Read it before changing tree construction, the viewer, recency, scopes, or worktree handling.

## Architecture invariant

Git output is the synchronous source of truth. The git-backed file tree renders first, and everything else (diffs, highlighting) arrives as independent async decorations over the stable tree, so the basic view never waits on them.

## Startup

**Whether stet can run at all is settled before the alt screen is entered.** The repository resolves in a preflight (`Git.repoContext`, and nothing else: a ref is never gated, see below) that runs on its own short-lived runtime, the same reason the config load has one: the first use of the app runtime builds `DiffEngineLive`, whose highlighter warm-up must stay behind the first paint. It is one O(1) git read, so the instant-paint shape is unchanged, and a launch outside a repository never flashes an empty shell before printing.

**Every way git can refuse becomes one actionable line, never stet's own invocation.** The classification is pure (`src/git/repo.ts`) and covers a missing git binary, a directory that is not a repository, a bare repository or the inside of a `.git`, and a git too old for `rev-parse --path-format`; anything else quotes git's first stderr line and nothing more, since the rest is the `use '--' to separate paths` boilerplate that made the original reports unreadable.

Two of those are read from a **signal git does not translate**, because its stderr is localized and matching English text would classify an English user and drop every other one into the unclassified branch. The too-old case is read off **stdout**: `rev-parse` echoes an option it does not recognize and exits 0, so an unusable answer arrives as success, which is why the parse requires two absolute paths (and why the message names the option git rejected rather than a minimum version stet has not proven). Bare-versus-absent is read off a second command's **exit code**, `git rev-parse --is-bare-repository`, asked only once the context read has already failed: exiting cleanly means git found a repository whose working tree is not here (a bare repository, or the inside of a `.git`), and failing means it found none.

**A ref the user named is explained by the diff that failed, never gated before one runs.** `rev-parse --verify` is wrong in both directions as a gate: it accepts any object, so a blob sha passes and the diff then dies with git's usage block, and it rejects a revision range (`main...HEAD`) and an unborn `HEAD` that `git diff` takes. Only the diff knows what the diff accepts, so the launch is never blocked on a ref; when the startup load fails, `Git.refIsDiffable` (a `^{tree}` check, exempting ranges) names the ref as `unknown git ref: <ref>` and otherwise the failure keeps git's own message. It answers `true` whenever it cannot tell, so it can only ever add an explanation. The `unstaged` scope never reads its ref, so a failure there is never attributed to one.

## Tree construction

- Source the tree from `git ls-files --stage` (tracked, carrying the file mode) plus `git ls-files --others --exclude-standard` (untracked, gitignore respected), union'd with the changed set so staged deletions stay visible.
- A symlink is identified by git mode `120000` for tracked files and by `lstat` for untracked ones; it renders with a distinct symlink icon, and its content/diff is the link's target path text (matching git), never the dereferenced target. The local-file read path uses `lstat`/`readlink`, so a link to a directory, a binary, or a missing target still reads as its one-line path.
- Trees orders directories before files, then uses natural, case-insensitive name ordering (`file2` before `file10`).
- Flatten single-child directory chains into one row. `state` owns the public `FileTree` model from `@pierre/trees` through `src/tree/model.ts`; OpenTUI reads visible slices and Trees' live expansion flags. Folder controls follow Trees: Right expands a closed folder or advances to the next row; Left collapses an open folder or focuses its parent; Enter toggles a folder. Home and End focus the first and last visible items. Activating a file records a viewer navigation. The adapter keeps model identities private so a deleted file and a same-named directory remain distinct, while all callers receive original Git paths.
- Tag each changed file with its stage state (staged, unstaged, mixed, untracked) from `git status`.
- Include untracked files in the changed set (except in the `staged` scope) and render them as all-added diffs.
- Go-to-file (`ctrl-p`) searches the same file universe as the tree.

## Scopes

`stet [ref]` defaults to `all` (worktree vs `HEAD`). `--staged` / `--unstaged` set the initial scope. `s` opens a scope picker (a static-list overlay like the worktree picker: `j`/`k` navigate, `enter` selects, `esc`/`s` close, opening on the active scope) over five scopes, in order: `all` (worktree vs `<ref>`), `staged` (`git diff --cached <ref>`), `unstaged` (plain `git diff`, ignores the ref), `session`, `last-commit`. The picker's explicit labels are what make `unstaged`'s ref-drop legible.

`session` ("since session start") diffs the worktree against the SHA `HEAD` pointed at when stet launched, captured once at startup and re-pinned on a worktree switch. Its base stays fixed as the agent commits, so it spans intervening commits plus uncommitted and untracked work: the full delta since you started watching. `last-commit` ("last commit") is the newest commit's own diff, `git diff <parent> HEAD`, with untracked excluded; on a root commit `parentRef` reports no parent and the base falls back to the repository's empty tree, so the whole first commit renders as all-added. Its right side is the literal `HEAD`, so it always follows the newest commit, and its parent re-resolves as `HEAD` moves so a new commit advances the window and re-keys the checks; a scope switch never registers as recency activity.

**A repository with no commits has no `HEAD`, so the base is resolved before the command is built rather than tolerated after it fails.** Every other `HEAD`-touching read degrades on exit 128 (`headRef` and `parentRef` to `undefined`, `commitsSince` to an empty set, `recentCommits` to an empty list), but a diff has no degraded answer: `git diff HEAD` simply cannot run, which is why the two model loads were the only calls left dumping git's raw `ambiguous argument 'HEAD'` at launch. So startup resolves `headRef` **before** `changedFiles`, and an unborn `HEAD` makes the base the empty tree, against which every tracked file reads as added and untracked files join the changed set as they always do. `all` and `staged` both take that base (`baseRef`, the memo over `headUnborn` and the CLI ref).

**Only the literal `HEAD` is ever substituted.** An orphan branch (`git checkout --orphan`) has an unborn `HEAD` in a repository whose other refs all still resolve, so a ref the user named is a working diff endpoint there; swapping it for the empty tree would silently show a wholly-added tree against nothing while the header claimed `no commits yet`. `headUnborn` therefore means "the base is `HEAD` and `HEAD` is unborn", not "`HEAD` is unborn", and every site that computes the base states that pair.

The substitution is transient in **both** directions, repaired off the refresh drain (`repairBase`, the shape `last-commit` re-resolves its parent with): a first commit gives `HEAD` a meaning and returns the base to the CLI ref, and a `git checkout --orphan` mid-session takes it away again. The second direction is only reachable from a **failed** read, since a successful one proves nothing changed, so the drain checks it on the failure path and checks the first only while the base is substituted; a repository with commits pays nothing. Without that second direction the drain failed on every tick with the tree frozen and no alert. The empty-tree base is stet's own, so it never renders as a sha: `scopeLabel` takes the repository's empty tree and names a ref equal to it `no commits yet`, which also keeps it from crowding the branch off the header. It compares the **scope's own ref**, never `headUnborn`: that signal describes the base `all`/`staged` would take, and a scope picked from the menu during the startup load keeps whatever ref it was given (the startup batch leaves a user-touched scope alone), so labelling off the signal there names a base git was never handed.

**The empty tree is the repository's, resolved once and never named as a constant.** Its sha follows the repository's hash algorithm, so a SHA-256 repository (`git init --object-format=sha256`) has a different one, and handing it the SHA-1 empty tree names an object its database does not contain: git rejects the whole command with `ambiguous argument`. The startup preflight therefore reads `--show-object-format` on the same `rev-parse` that resolves the repo root, and `RepoContext.emptyTree` carries the answer into `state`. It is resolved once for the session, including across a worktree switch, since linked worktrees share one object database. Correspondingly nothing in the git service names an empty tree at all: `headRef` and `parentRef` report `undefined` for "no commit" and `Commit.parent` is optional, so the substitution happens only where a diff endpoint is built (`baseRef`, `selectScope`, `selectCommit`, `rebaselineScope`, `repairBase`, and startup). The drain's `last-commit` re-resolve compares against the **substituted** ref, never the raw parent: on a root commit the parent is absent while the scope holds the empty tree, so comparing the raw value would re-set the scope on every tick and reset the viewer's cursor and scroll each time.

The picker is two levels: `enter`/`right` on its trailing `commits →` row drills into the last `LIMIT` commits (`git log`, newest-first, loaded on open; `esc`/`left` backs out), and selecting one applies a sixth scope, `commit`, that shows that commit as its own diff. A `commit` scope is `git diff <parent> <sha>` (the commit's first parent captured from `%P`, or the repository's empty tree when `%P` is empty, a root commit), reusing the `last-commit` range machinery: neither endpoint is the worktree (the left one is the parent commit, or the empty tree at a root commit), so untracked files are excluded, and it is not a top-level picker row (never applied except through the drill-down). It is pinned by SHA, so it does not follow `HEAD`; a worktree switch resets it to `all`. That reset is a change of inspection context, not a resolution failure: linked worktrees share one object database, so the SHA still resolves in the target, but it was picked out of the history the user just left. The header names the active commit by its subject; the commit list is a snapshot, so a commit made after opening the drill-down appears on the next open.

## Worktrees

`w` switches the active worktree in place and re-points the tree, diffs, and refresh (watcher and poll) at it, with no restart. The switch loads only the changed set up front (the same shape startup seeds), so it re-points the instant the cheap diff commands resolve rather than blocking on a full `git ls-files --stage` over the worktree; the full tracked-file tree fills in on the repoFiles refresh (triggered on the re-key, then whenever the changed path-set shifts, plus a slow floor), exactly as at startup. The picker lists worktrees from `git worktree list --porcelain -z` (bare entries excluded) and marks locked and prunable ones.

Each worktree also carries a **summary** (`src/git/worktree.ts`, pure): `lastActivityAt`, when an agent or git last touched it. This is how stet answers "which worktree is an agent working in", and it stays inside the read-only, no-agent-integration guardrail: it never looks for an agent, only at what one leaves behind, so it works in any git repo.

**Activity is the most recent of three signals, and needs all three.** The obvious one, the newest mtime among the worktree's uncommitted files (`git status --porcelain=v1 -uall -z`, one call per worktree; `-uall` so an untracked directory is not collapsed to a `dir/` whose own mtime would not move when a file deep inside it is written), is on its own **actively wrong**: it goes to zero the moment an agent commits, which is exactly when the worktree was busiest, so a just-finished agent's worktree reads as dead. So it is maxed with the **`logs/HEAD` reflog mtime** (a commit, checkout, reset, rebase, or the worktree's own creation), a free `statSync` whose git dir is resolved without git (`<worktree>/.git` is a directory in the main worktree and a file naming the real dir in a linked one), and never rewritten by a `git status`, unlike `index`, so stet's own polling cannot fake activity into it. **HEAD's commit time** is the portable floor beneath the reflog for a repository with `core.logAllRefUpdates` off, fetched for every worktree in **one** subprocess (`git show -s --format='%H %ct' <sha>…`, using the HEAD shas `parseWorktreeList` already parsed, since all worktrees share the one object database). Every value is a real timestamp, **never the moment we noticed**, so a poll that runs late still reports an exact age.

Summaries are polled, not watched (only the active worktree earns an fs watcher), every `PEER_SUMMARY_MS` on a background fiber keyed on `repoRoot` like the refresh loop. The `git worktree list` on each tick is also the discovery mechanism, so it cannot be resolved once at startup: an agent can create a worktree mid-session. It is a cheap directory read, and a repository with a single worktree stops there, never paying for a `git status` it has no peer to compare against. `mergeWorktreeSummaries` keeps the previous map when nothing moved, so an idle repository's poll wakes no renderable.

A worktree stays active for **`WORKTREE_ACTIVE_MS`** (5 minutes), deliberately far longer than the 30s `RECENT_MS` a changed _file_ stays fresh for: that window is tuned to flash a row in the tree, whereas an agent pauses for minutes at a time (thinking, running tests, waiting on a build) and is plainly still working the whole time. Because the two windows differ, `recencyFraction` takes an optional `window` (defaulting to `RECENT_MS`, so the tree, file picker, and status bar are untouched); without it a worktree an agent is plainly still working in would grey out after 30s.

The **picker** is the one surface that reads the summaries, and it answers the whole question (_which_ worktree, not merely how many). Its row is the branch, its `locked`/`prunable` badges, and its age (`relativeTime`: `now`, `5m`, `3h`), tinted on the recency ramp over `WORKTREE_ACTIVE_MS` (`recency.fresh` fading into `recency.aged`, which is where `text.faint` sits) so a worktree an agent is working in glows and cools as it goes quiet. The age carries the recency rather than a `RecencyDot`, because `●` already means "current worktree" in this row and one glyph may not carry two meanings; the word is the signal, so the row reads under `NO_COLOR`. There is deliberately **no changed-file count** (a column repeating `clean` answers a question nobody asked) and **no per-row path**: the worktrees of a repository share a long common prefix, so a path left-truncated to a fixed column slices that prefix at a different offset on every row (`…trees/`, `…ude/`, `…ees/`) and cuts the leaf, the only part that differs, while no in-row path can fit anyway. The full path of the **highlighted** worktree instead gets its own fixed-height row above the instruction hint, where a real path fits the overlay's width complete and untruncated. Rows are ordered by `orderWorktrees`, purely by how recently each was touched, with **no pin for the main worktree** (it is only the busiest worktree when it actually is). That order is computed **once, when the picker opens**, never on a summary refresh, so the list can never reorder under the cursor while it is open; the cells themselves stay live.

Typing filters the rows by a case-insensitive subsequence over the branch label plus the path's **distinguishing tail** (`worktreePathTails`: the segments after the prefix every worktree shares, compared segment by segment so a shared parent cannot slice a leaf mid-name). The shared prefix is deliberately **not** in the haystack, for the same reason it is not in a row: it is the identical text in every entry, so as filter text it can only ever match all of them at once (`dev` matching every worktree through `/Developer/`), never separate two. The tail is the only part that distinguishes, so it is the only part worth matching. The main worktree, when the others are nested under it, has no tail at all and narrows by its branch alone.

Every picker cell is a fixed-width `<box>`, never a padded string, and the width budget subtracts **four** cells from `overlayWidth`: two for the overlay's border and two for each row's own padding. Both rules are load-bearing and each has already caused a bug. A whitespace-only `<text>` measures zero cells in a flex row, so a padded empty cell slides every column right of it out of line; and budgeting against the padding alone overruns the row by exactly the border, which the renderer silently clips off the right edge (it ate the last character of every path).

The **header carries no activity cue**, and should not grow one back. It briefly shipped an `N worktrees active` line, which crowded the densest row in the app: joined to the identity by the same separator that splits repo from branch, it read as a third peer token beside them, and it answered only the weaker half of the question (how many, never which). The picker answers the whole of it, so the header stays git identity.

If the active worktree is deleted out from under stet mid-session, the always-on refresh heartbeat is the detector: a git failure where the worktree root, or the repository's main worktree, no longer exists flags the deletion (every subprocess fails fast with a clear "working directory no longer exists" message rather than a raw `posix_spawn` error, because `Process` guards `cwd` existence before spawning). stet then auto-switches to the main worktree. The main worktree is resolved once at startup from the common dir (`git rev-parse --git-common-dir`, the `<main>/.git` whose parent is the main worktree) and lives outside any linked worktree's tree, so it survives that worktree's deletion without needing to be re-queried. When the main worktree itself is gone, the repository is gone (every linked worktree's git points into the deleted `<main>/.git`), so stet exits cleanly with a one-line message instead of looping on the dead directory.

## Overlays

Every overlay (the go-to-file `FileCombobox`, the `ScopeMenu` and `WorktreeCombobox`, the `HelpDialog` keybindings reference, and the `ThemeCombobox`) reads as one command-palette family: a centered bordered box at the shared `overlayLeft`/`overlayWidth` and `zIndex 100`, a list, and a muted instruction-hint footer at the bottom (`↑↓ navigate · ⏎ <verb> · esc close`, tailored per overlay and naming only the keys that overlay actually honors). Input-driven overlays (`FileCombobox`, `ThemeCombobox`, `WorktreeCombobox`) are title-less, the filter placeholder is their label; the fixed `ScopeMenu` and the `HelpDialog` carry a short action-verb title (`switch scope`, `keyboard shortcuts`). `esc` is the canonical close on all of them. The `HelpDialog` stays a read-only, dismiss-only reference (no filter input, so it is a dialog and not a combobox) and groups its keybindings under calm muted section labels (`navigation`, `viewer`, `tabs`, `workspace`, `layout`, `app`), spaced one row apart, rather than as one flat list; its entries come from the shared `KEY_HELP` registry (`src/help/keys.ts`) that `stet --help` also renders, so the overlay and the CLI help can't drift. The chrome is deliberately inlined per overlay for now (a shared overlay-shell component is a future extraction), so each overlay owns its own rows, swatches, and hover-preview.

## Theme switcher

`t` opens a theme switcher (an input-driven overlay like the go-to-file palette: a filter input, `↑`/`↓` or `ctrl-n`/`ctrl-p` navigate, `enter` applies, `esc` cancels), listing an `auto` entry (follow the terminal) followed by every registered theme (`system` when the terminal reported its palette, stet's built-ins, the bundled highlights themes, then user theme files). It is a runtime, session-only control: it writes nothing to disk, so a restart returns to the config selection. Navigating previews live, the highlighted theme becomes the active selection so the whole UI and the diff re-theme instantly through the one reactive seam (the same `selection` signal the config seeds and the appearance flip drives); the wheel and hovering a row drive the same highlight, so a pointer previews as it moves. The selection active when the picker opened is captured as the revert target: `esc` (or any cancel) restores it, `enter`/click commits the highlighted one. A single picked theme is a name, never a `{dark,light}` pair (that stays a config-only construct), so opening on a pair highlights the row of the theme it renders for the current appearance, and keeps the pair as the cancel target.

## Live view

Refresh the tree, diff, and file content while the user watches. A debounced filesystem watcher (the worktree tree plus the resolved git dir, so staging in a linked worktree is seen) re-derives git state the instant a change lands; a slow safety poll is the floor that covers anything the watcher misses, so the worst case is poll-speed, never stale. The watcher ignores high-churn git internals an agent generates while it works (loose objects, reflogs, `*.lock` files, rebase/merge scratch, `COMMIT_EDITMSG`, `FETCH_HEAD`), which never change the rendered state; staging/commit/checkout still tick via HEAD, the index, and refs, and anything wrongly filtered is still caught by the poll floor. Preserve selection by path and the cursor across refreshes; reset the cursor only on a file switch. A refresh never writes the repository: no git child takes `.git/index.lock` (an agent's concurrent `git commit` would fail on it), and the reads that need git to refresh its stat cache run against stet's own copy of the index, so a file whose mtime moved without its content is neither listed as changed nor re-hashed on every tick.

## Viewer

- Unchanged files render full content read-only. `v` toggles a changed file between diff and full content.
- Full files render through the diff viewer as synthesized all-context patches.
- Per-file diffs are computed in-process, not via `git diff <ref> -- <path>`: `fileDiffSides` (`src/git/file-patch.ts`) resolves the scope's two endpoints (a `git show <ref>:<path>` / `:<path>` blob read on each committed/indexed side, a raw worktree read on the worktree side), and the diff engine diffs the two texts itself (`parseDiffFromFile` on `@pierre/patches`, with git's three lines of context). In very large repos git's pathspec-limited diff-index walks the whole index (seconds per open), while a blob read stays O(path depth). The pathspec `git diff` invocation survives only as a fallback for the cases an in-process diff can't reproduce faithfully: a side that is missing/oversized, one-sided CRLF (git may eol-convert the worktree before diffing), identical text against non-zero numstat counts, or a worst-case diff cost over budget. The diff has no deadline, so the cost `(N+M)·D` is bounded before diffing, with `D` bounded from the text (the lines between the common leading and trailing characters, or `N + M - 2L` over patience diff's common subsequence: the order-kept lines unique to each side plus the equal lines at either end of each gap between them); a one-sided add or delete is linear and exempt. Binary files (flagged by numstat) skip the diff and instead fetch both sides' size and image dimensions (`git.binaryMeta`, reusing the same side reads) for the metadata surface below; untracked files keep the existing `git diff --no-index /dev/null <path>` path.
- The diff is rendered by stet's own windowed renderer (`src/diff/`, `src/components/diff/diff-view.tsx`) on `@pierre/diffs` (headless parse + highlight on its `highlights` backend) and OpenTUI primitives, not the built-in `<diff>`. Invariants that keep it from wedging OpenTUI's scheduler: the line-number gutter is padded to a file-wide fixed width (never sized from the visible slice, so it never oscillates); only the visible row slice plus a small overscan is mounted, with top/bottom spacer boxes standing in for the off-screen rows so total scroll height is exact; in non-wrap mode each row is pinned to a single terminal row, so the spacer and `maxScrollY` math stays exact even when a grapheme (e.g. a variation-selector emoji) would otherwise lay a horizontally-clipped line out two rows tall and strand the file's last line; and each selection commits once, already highlighted, holding the previous snapshot until it resolves. Each paired removed/added line marks its changed words (`@pierre/diffs`' `word-alt` inline diff, carried as `RenderSpan.changed`) with the line's sign color layered at 20% (dark) or 15% (light) over the row's own background, the normal or the lifted cursor/selection one (`theme.rgba.*WordBg*`, derived in `resolve.ts` the way diffs.com does, so no theme needs new tokens); the caret word's background wins over it. The mark is background only, like the line tint under it, and costs comment text some contrast (about 2.2:1 on a changed word). Vertical scroll is the scrollbox's native scroll mirrored into the window; long lines scroll horizontally via a shared `scrollX` offset that shifts every visible line together while the gutter stays fixed (wrap mode reflows instead). Syntax covers every language `@pierre/highlights` has a lexer for (~150, all bundled, so nothing is loaded on demand or warmed per language); a language it lacks renders as plain text without blocking the render. `languageForPath` is the syntax adapter over the shared file-support association cascade; exact filename, glob, extension, and dotfile rules may override the final `@pierre/diffs` filename inference.
- Binary files render a metadata surface, never raw bytes: `BinaryPreview` (`src/components/binary-preview.tsx`) centers the file type, image dimensions, and human-readable size (`imageMeta` reads dimensions from the header bytes of PNG/JPEG/GIF/WebP/BMP, no decode; SVG stays text), in file-content mode from the single viewed side and in diff mode as an old -> new delta, with an "open externally" affordance. It is the metadata an IDE shows for an image, which stet does not draw as pixels, and it reserves the full viewer height so opening a binary never shifts layout. `O` (or the context menu / the `openExternal` command action) opens the file in the OS default app. Missing and oversized files render a short placeholder line. A file whose diff or content exceeds the render cap loads partially; a reserved footer row at the bottom of the viewer names the hidden-line count (`⋯ N more lines · f to load`) and `f` (or a click on the row) loads the rest. The footer is a standing property of the current file, so it lives at the content, not in the transient status bar; the row is reserved out of `viewerHeight`, so the diff never shifts under it.
- `/` opens an in-buffer find over the rendered lines: smart-case substring match (case-insensitive unless the query has an uppercase char), `n`/`N` cycle, `esc` clears, and a file switch ends it. An open (uncommitted) find bar also closes when focus leaves the viewer, since it owns the keyboard; a committed find stays. Matches are highlighted at the line level; substring-range highlighting within a line is out of scope for v1.
- **Collapsed regions** fold or expand runs of lines behind a single non-navigable marker, all through one pure transform (`applyCollapsedRegions`, `src/diff/regions.ts`) over the raw row stream. Two kinds with opposite defaults, two `Set`s of keys: a **user fold** starts expanded and `z` at the caret collapses it behind `▸ N lines folded`. The region model is language-aware (`foldRegionsFor` dispatches on the file's `languageForPath`): code folds by indentation (`computeFoldRegions`, a line whose following lines are more indented heads a region), while markdown folds by heading section (`computeMarkdownFoldRegions`, an ATX heading down to the next same-or-higher heading, fence-aware). The other kind, a **git gap** (elided context, including the stretch after the last hunk), starts collapsed as `⋯ N unmodified lines` and `z` (or a click) expands it, revealing the whole gap's unchanged lines, syntax-highlighted, behind a `⋯ hide N unmodified lines` marker. Gaps come from `@pierre/diffs`' `DiffHunksRenderer` over a diff built from both files' full text, so revealing one is synchronous, with nothing to load; a 1-line gap renders inline. A gap is expandable only when the file was diffed in-process from those texts; a git fallback patch (a cost over budget, one-sided CRLF, a content filter, a missing or oversized side) runs through textconv and clean filters, which can renumber lines, so it carries no files and shows a plain `⋯ N unmodified lines` separator, as git's own `@@` jump does. A file whose new side lacks a final newline ends with git's `\ No newline at end of file` row. `z` unfolds a folded header, else folds the region enclosing the caret, else toggles the gap nearest the caret; clicking any marker toggles it. **Invariant:** the caret indexes only visible lines. The transform re-densifies each surviving line row's `navIndex` and rebuilds `navigable`, and every toggle remaps the caret to its file line (or the fold header when that line is now hidden), so the caret can never land inside a fold. Folds/gaps are per file and reset on file switch; a jump whose target line is folded clears the covering fold so it can still land (`revealLineForJump`). Wrap moved from `z` to `x`.
- The viewer carries a **word-granular caret** on the cursor line: `h`/`l` (and `←`/`→`) hop it identifier to identifier (`src/diff/words.ts`), wrapping across line boundaries (past the last word to the next line's first, past the first to the previous line's last), and the word it owns gets a cool neutral background highlight (`markRange` in `src/diff/spans.ts`, the `caret.wordBg` token); `Tab` moves focus to the next pane (`h` no longer does). The caret is stored as a **precise UTF-16 offset** (`cursorColumn`), so a search jump lands on its exact column and copy emits `path:line:col`, but motion and the highlight are word-wise. It homes to the line's first word on every vertical move (`setCursorRow`) and a content reload; a jump snaps it to the word owning the target column. A click on the line-number gutter instead selects the line with **no word** (`caretLineLevel`): nothing highlights and `y` copies `path:line` rather than `path:line:col`; the next caret motion or content click re-selects a word. Two derived signals split the concerns: `caretWord` ("is the caret on a word, and which") drives the highlight, while `caretColumn` (gated only by `caretLineLevel`, not by landing on a word) drives the `:col` in copy, so a search jump that lands in a gap still reports its exact column. Horizontal follow keeps the caret word in view (`followScrollX`); the word highlight follows the word through wrap, but horizontal follow is scroll-mode only.

## Navigation and tabs

The viewer is a set of tabs, each an ordered history of Locations (a Location is what restores the view: path, cursor file-line, caret column, scroll, and the `v`/`f` toggles). The pure model lives in `src/viewer/navigation.ts`; `state` keeps the live signals (`selectedPath`/`cursorIndex`/scroll) as the source of truth and the history as an orthogonal recorder that captures a Location on leave and applies one on arrive.

- **One preview tab.** At most one tab is the ephemeral _preview_ (rendered italic, the standard ephemeral-tab cue, which frees the color channel so a previewed changed file still shows its diff tint). All navigation (tree browse, jumps, palette, search, `.` recency) targets the preview tab and replaces it in place: continuous tree browsing coalesces into one history entry, a deliberate jump pushes (truncating forward entries, browser semantics). Browsing never spawns or duplicates tabs; this is the calm single-buffer feel by default. The strip earns the viewer's title row only once a tab is pinned; a lone ephemeral preview shows the path instead.
- **Pin/unpin (`ctrl-t`).** Toggles the active tab. Pinning the preview makes it persistent and the next navigation opens a fresh preview; unpinning a pinned tab reverts it to the (sole) preview, discarding any stale preview so exactly one exists. Navigating to a file already open in a _pinned_ tab focuses that tab rather than previewing it, so a file is never in both the preview and a pinned tab. Double-clicking a tab in the strip or a file in the tree pins it too (pin-only, never unpins, unlike `ctrl-t`'s toggle); OpenTUI has no double-click event, so it is detected from successive mouse-downs.
- **History and tabs (`<`/`>`, `{`/`}`, `ctrl-w`).** `<`/`>` move back/forward within the _active_ tab's own history (no truncation), restoring that entry's exact cursor and scroll. `{`/`}` cycle tabs with wrap; `ctrl-w` closes the active tab; closing the sole remaining tab reverts it to the preview (a view always exists, so the floor is the ephemeral preview).
- **Remembered position.** A global per-path MRU viewport (cursor file-line + caret column + scroll), shared across tabs, is written on every navigate-away. A _fresh_ visit to a path restores its MRU position; back/forward restore the exact spot recorded on the history entry instead. Cursor is a file line (stable across refreshes); scroll is best-effort.
- **Coherence.** Scope stays a global lens, never captured per tab or per Location. Refresh and scope changes never reset the history (only a `navigate` resets). A worktree switch resets navigation to a single fresh tab seeded with the new worktree's selected file. The tab strip is chrome (non-selectable); tab hierarchy is typographic, not chrome: no tab backgrounds and no header band, the active tab is the one full-strength label (the others recede to muted), the active shows its full path while inactive tabs show the basename, and the preview tab is italic. Diff status is not on the strip; it lives in the tree and the viewer stats.

## Content search

- `ctrl-f` opens the project search pane, the first **main-area view mode**: a `mainView` union signal (`"file" | "search"`) swaps the Viewer's interior, so exactly one view is ever active and future panes extend the union rather than adding booleans. The pane is persistent: closing it (`esc`, or any navigation to a file, including a result jump) keeps the query, results, selection, and collapsed groups, so `ctrl-f` after a jump restores the result set instead of clearing it. A worktree switch clears the snapshot (stale paths) but keeps the query.
- The engine is `git grep` (`-I` to skip binary, `--untracked` so it covers the tree's universe, `--column` for the match column). It searches working-tree file content, not diffs. Literal `-F` with smart-case by default; a regex toggle (`ctrl-r`) swaps `-F` for extended regex `-E`, and a case toggle (`ctrl-x`) forces case sensitivity over smart-case. `--column` reports a byte offset; it is converted to UTF-16 units so a jump lands the caret on the exact column even on non-ASCII lines.
- Scope defaults to the changed set (pathspec-limited to `git status`'s changed files, so it follows the active all/staged/unstaged scope); `ctrl-g` toggles between the changed set and the whole repo, and `ctrl-s` opens the scope picker without leaving the pane; the scope cell names the effective universe (`repo`, or the active diff scope: `changes`, `staged`, `unstaged`, `session`, `last commit`). A filter field narrows by pathspecs (space-separated, git wildmatch): plain tokens include, a `!` prefix excludes (mapped to git's `:(exclude)`, so includes union and excludes subtract; an exclude-only filter matches everything else, and raw pathspec magic passes verbatim). Under the changed scope the filter drives the grep and the changed set filters the results after, since include pathspecs union rather than intersect.
- Results group by file with per-file headers (match count, collapsible with `enter`/`h`/`l`), two lines of context around each match (overlapping context ranges merge into one excerpt, `⋯` separates non-contiguous excerpts), and syntax highlighting per file language through the diff's shared highlighter (highlighted on demand for the visible window; rows render plain and upgrade in place). Context comes from bounded file reads, not `git grep -C` (whose `-z` output makes match and context records indistinguishable); an unreadable or oversized file degrades to match-only rows. `enter` routes through the shared `jumpTarget` path, landing on the line and column and escalating to full-file view when the line is outside the diff.
- Keyboard while the pane is focused: `tab` cycles query → glob → results, `↓` enters the results, `j`/`k` walk navigable rows (matches and headers; context and gaps are skipped), `ctrl-d`/`ctrl-u` half-page by _viewport_ rows (snapping to the nearest navigable row). Only the query/glob inputs swallow printable keys, and they keep their readline chords (`ctrl-a`/`ctrl-e` line home/end, `ctrl-w`/`ctrl-u`/`ctrl-k` kill); `ctrl-p` (palette) and the deliberately stolen `ctrl-b` (sidebar, with preventDefault) pass through even there. In results focus unhandled keys fall through, so the global bindings (`q`, `?`, `ctrl-p`...) keep working. A single click on a result selects it (a focus-intent click never navigates the view away); a double click, like `enter`, opens it. `esc` closes the search view and never quits. File-view keys (`v`, `f`, `z` fold, `x` wrap, `ctrl-t`/`ctrl-w` tab pin/close, `y`/`Y` viewer copy) are inert while the search view shows, since they would act on a viewer that isn't on screen; in the results, `e`/`o` open the selected result in the editor, `y` copies its reference (`path:line:col` on a match), and `g`/`G` jump to the first/last result. Any navigation to a file (a result jump, the palette, recency, history) reveals the file view, including a jump that lands on the already-selected file. The chrome rows (query, filter, summary, footer) are fixed-height in every state, so idle/searching/no-matches/error swaps never shift layout.
- The query is debounced and runs through the interruptible `Process` service, holding the previous snapshot until the new one resolves; a failed grep (a half-typed regex) keeps the prior results under an error notice. While the pane is open the search re-runs on every git-model refresh (and on reopen), so results, context lines, and jump targets track the working tree as an agent edits it. Results are capped to keep the pane bounded; hitting the cap is surfaced as a trailing `+` on the count.

## Layout

The shell is two panes, the tree and the viewer, between a fixed header row and a fixed status row. Geometry has exactly one owner.

- **Terminal dimensions become pane geometry in one place, `computeLayout`.** It partitions the terminal into the header, the tree, the viewer, and the status bar, returning each as a rect in absolute terminal cells plus the `content` rect it may paint. The panes have no box: the viewer paints its whole rect, and the tree gives one cell to the divider on the side facing the viewer. The header and status regions are one row each, and each is drawn as a rule with its text inset. The regions tile the terminal exactly: every cell belongs to one region, with no overlap and no gap.
- **No renderer re-derives a budget from the terminal size.** A surface that needs its usable columns reads its rect; it never subtracts a pane's width from the terminal's. This is enforced by there being no `sidebarWidth`/`paneHeight` accessor to subtract, not by convention, because the same expression once lived in five files with five different constants, which is what pinned the tree context menu to a hardcoded column and froze a list's follow viewport against a terminal resize.
- **The model stops at the pane's rect.** Chrome a pane owns inside its own rect stays with that pane: the viewer's title row and truncation footer, the search view's four chrome rows, a tree row's padding.
- **The tree's edge is a setting and a key.** It docks to `left`, `top`, `right`, or `bottom`, from `sidebar.position` or by cycling it clockwise with `d`, so one press is a 90 degree turn to an adjacent edge and four return it home. A closed tree does not move. The viewer takes whatever the dock leaves.
- **The tree is the one sizable pane**, sized along the axis it is docked to and remembering that size **per axis**: 50 columns is not 50 rows, so moving never converts one into the other, and a size set on one edge is still there when the tree returns to it. Reset clears only the docked axis, which is what makes a four-press round trip idempotent. The step, the minimum, and which override applies all follow the tree's current edge, so a top-docked tree resizes in rows against the row floor. The viewer is whatever the dock leaves, so it has no size of its own and the resize keys act on the tree from it too.
- **The horizontal default is responsive and the vertical default is flat**, because a row is an indivisible unit of content (ten rows means ten entries visible) while a column is not (more columns is just more of a path surviving truncation). Both defaults belong to the axis, not to a pane.
- **A pane cannot squeeze the viewer out of the terminal.** A manual size is stored raw and clamped only at layout time, so it never overflows a shrunken terminal yet is restored intact when the terminal grows back. The clamp reserves the viewer a minimum on both axes. When the terminal cannot afford both minimums at once, the tree falls back to its own and takes what is there. Shrinking the tree past its minimum closes it rather than clamping, and moves focus to the viewer.
- **`tab` switches between the tree and the viewer, landing on the tree only while it is open**, so focus can only ever name a pane something is drawn in. That is the invariant the rest of the layout leans on: closing the tree moves focus off it, a worktree switch seeds focus the same way, and zoom needs no open-flag check of its own because the pane focus names is always one it can paint. Open, not painted, is the test, since zoom hides the tree without closing it and `tab` carries the zoom along rather than being trapped in whatever it lit up. The search view keeps `tab` for its own three fields, the conventional meaning inside a form, so the switch never starts there; `esc` and `ctrl-b` still leave it.
- **Zoom is a layout input, not a change to which panes are open**, and it **follows focus** rather than pinning a pane: one key gives whatever is focused the whole band, so switching focus moves the zoom with no rule of its own. It needs no open-flag check because focus never names a closed pane, so restoring is clearing it and a toggle pressed while zoomed cannot strand a stale visibility flag.
- **Actions that change pane visibility exit zoom; actions that only move focus carry it.** Opening or closing the tree while zoomed would land invisibly and surprise on the way out, so the toggle clears zoom first. The geometry keys instead do nothing at all while zoomed: resizing a pane that already fills the screen is meaningless, and a hidden tree is not closed, so a write there would be invisible.

## Header and status bar

The two bars split by lifetime, and neither takes the other's job.

- The **header** is durable context: repo or worktree identity, branch or commit subject, scope, and changed count. It changes only when the thing it names changes, carries no live cue, and is never where progress or an outcome is reported.
- The **status bar** is live: it renders exactly one full-width item, chosen from a fixed ladder, and never splits guidance beside content. In order: foreground progress (a worktree switch), an action notification, a persistent alert, recent activity, then guidance.
- **Guidance is the lowest tier and always has content**, which makes the selection total and every tier above it a pure displacement. It is context-aware only for the temporary find modes (`enter find ─ esc cancel` while entering, `n/N next/prev ─ esc clear` while navigating matches) and is otherwise `? help ─ q quit`. Any live content replaces it across the full row, and it returns once nothing is live. The panes get no standing tutorial hints; overlay controls stay in their overlay footers.
- **Routine successes are not status.** A completed worktree switch reports nothing: the durable UI it just updated is the completion signal, and a persisted success line outlives its usefulness.
- **Only warnings and errors persist**, as an alert tagged by its lifecycle (`worktree-list`, `worktree-switch`). Each source retires its own alert when its next attempt starts, and clearing one never clears another's; a failed list and a failed switch are separate sources, so browsing the picker cannot retire an unretried switch error. When two are raised the newest owns the row, since one row cannot rank them. A switch shows `switching to <label>…` as foreground progress and leaves nothing behind on a normal success; list, missing-path, and switch failures persist until their retry starts, and only the latest request may clear progress or raise. A switch nobody asked for (recovering from a deleted worktree) is the exception that does announce itself, as a brief warning notification.
- Fit is measured in terminal cells, never string length.

## Recency

Recency markers come from an append-only in-memory activity event log (the seam for a future persistence layer). They decay silently: fresh under 5s, recent under 30s. `.` jumps to the latest activity. A scope switch is not activity. The status bar surfaces that latest activity, the most recent changed file, whenever nothing more acute is live, presented like a tree row: the path in its git change-kind color plus a recency dot, both fading toward the background across the window (no elapsed-time number), so it reads as a changed file and recedes silently as it ages.

## File support

- Syntax and icons resolve through one named association cascade in `src/file-support/`. An association may select exact `filenames`, basename or repo-relative `globs`, bare `extensions`, and the unmatched `dotfiles` class. Specificity is exact filename, glob, extension, dotfile, then fallback. Later user associations win a tie, user entries layer after built-ins, and matching is case-insensitive unless the association opts in with `caseSensitive`. The two facets resolve independently. A facet set to `false` blocks every lower match and yields plain text or the generic file icon. Syntax otherwise falls back to `@pierre/diffs` filename inference, except a bare dotfile never masquerades as an extension; icons fall back to Trees' `complete` resolver. Trees owns default name and extension matching; a terminal adapter maps its tokens to named glyphs and colors, with the generic `file` glyph for unrecognized types. Explicit icon facets override Trees defaults.
- Two config registries share the same named layering rule: `files` for associations and `icons.glyphs` for raw glyphs. A same-name object partially overrides its built-in, arrays replace, a new name adds, and `false` disables. Invalid whole-entry overrides surface a notice while retaining the built-in; an unknown icon or syntax reference on a file association drops only that facet. The config loads once at startup, and the registries remain fixed for the session.
- Icon names and glyphs are independent from associations. `file`, `folder`, `folder-open`, and `symlink` are ordinary built-in names. `theme.icon` is a dynamic color map over those names and user names; a missing color falls back to `text.muted`. Built-in file types take the terminal hue that suits them (`ICON_HUES`), so they follow each theme's palette, while `config`, `document`, `file`, `folder`, `folder-open`, `font`, `lock`, `symlink`, and `template` intentionally stay muted. Every colored built-in icon maintains at least `3:1` contrast against the base, panel, and cursor surfaces in `stet-dark` and `stet-light`, and every built-in icon is audited as colored or intentionally muted. Every list surface uses the shared fixed 2-cell `FileIcon` with the full repo-relative path, so path globs, `--no-icons`, theme switching, and terminal appearance changes stay consistent without shifting text.

## Version awareness

- The latest version comes from GitHub Releases (`tag_name`, strip the `stet-` release-please component prefix, then a leading `v`, so `stet-v0.5.0` parses), the canonical source the install script, the brew tap, and npm all derive from. The lookup is a plain `fetch` (`src/upgrade/release.ts`) with a required `User-Agent` header, bounded by a timeout, and resolves to `undefined` on any failure. There is no cache: the check runs on every launch and fresh on every `upgrade`.
- The background check runs once on launch, non-blocking and independent of the git load. A newer release is held in `availableUpdate` and printed once on a clean keyboard quit (`q`/`esc`/ctrl-c), after the alt-screen is restored. It never prints on a crash or external kill (those backstops do not route through `quit`), and never interrupts the running session.
- `stet upgrade` compares the current version against the latest before spawning: when the latest is not newer it prints `stet X.Y.Z is already up to date` and exits without running the channel update; when the check fails (no network) it falls through to the channel update, leaving each tool to resolve `@latest` itself.
